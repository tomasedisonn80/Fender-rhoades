# VST3 MIDI interoperability continuation

Status: reviewed design in progress; implementation and acceptance results are
recorded separately. Baseline: `20a77e8b2033d435839df594c783837befb07938`.

## Scope

Improve the existing three synthetic instruments' host interoperability. The
mechanical models, pickup equations, filter coefficients, class identities,
latencies, gain/sustain IDs and 16-byte saved configuration remain compatible.
Contact and numerical-reference research continue in their separately owned
tasks. This work does not establish measured Rhodes fidelity or DAW qualification.

The baseline Linux/GCC Release build with the pinned SDK passed 301 CTests,
including the three SDK validators and module metadata checks. The baseline
controller nevertheless accepts `nan` and numeric prefixes such as `16junk`
through its inherited gain text parser. Well-formed polyphonic pressure also
rejects its entire input block, including any accompanying note releases.

## Channel All Notes Off

Expose 16 nonautomatable, writable command parameters through `IMidiMapping`,
one for MIDI CC123 on each channel. Reserve IDs `0x1000..0x100f`; existing gain
and sustain retain IDs 0 and 1. These commands use `kNoFlags`, not hidden or
read-only flags. They are transient commands, excluded from saved configuration.

Every delivered command point triggers a channel release, including zero and
repeated values. Do not infer a rising edge or interpolate command values.
Validate every point before changing ownership. At an equal sample offset,
sustain takes effect first, channel releases follow in ascending channel order,
then note messages follow their original list order. A new strike at that offset
therefore survives the preceding channel release. Duplicate commands for the
same channel and offset have the same result as one command.

Remove only that channel's note holders. Send an ordinary physical note release
only when the last holder of a key disappears. Preserve the shared sustain
configuration, mechanical state, and convolution tails. CC123 is not a panic or
All Sound Off command; CC120 remains unmapped.

Allow at most 18 parameter queues, 256 total command points and 256 input events.
Keep the existing 8192-point limits for gain and sustain. Expansion to physical
releases uses fixed storage and preserves the 256-action per-sample dispatch
limit, including sustain. Complete syntax preflight precedes the mailbox token;
ownership preflight uses that token's selected recall and can abort it without
discarding a newer recall. Live-state changes start only after both checks pass.
Invalid or over-budget inputs reject atomically.

Zero-frame parameter flushes accept only offset-zero points and reject nonempty
event lists. Apply a selected recall first, then final gain/sustain and staged
channel releases. Ordinary releases do not advance mechanics, frame cursors or
filter history; a selected recall intentionally resets them. Unexpected release
failure fences further processing and publishes the accepted partial state;
it does not roll back an already accepted transaction. Native DAW tests
must separately establish whether each host delivers repeated unchanged CC123
values: a plug-in cannot recover controller messages omitted by its host.

## Polyphonic pressure

Accept well-formed `PolyPressureEvent` as a validated no-op in the current
synthetic model. Validate its bus, ordering, sample offset, finite PPQ, channel
0..15, pitch 0..127 and binary32 pressure 0..1. Keep all signed note IDs legal,
including -1. Pressure counts toward the existing 256-input-event budget and
updates the ordering cursor even though it emits no physical action. It does
not change note ownership or advertise pressure-responsive synthesis. Other
unimplemented event kinds retain their existing rejection contract.

## Generic control text

Both text APIs must reject invalid parameter IDs, nonfinite/out-of-range values,
null pointers and uninitialized controllers without changing caller output or
saved configuration. Gain input must consume a bounded ASCII decimal entirely,
independent of locale, allowing a leading sign, decimal fraction/exponent,
surrounding ASCII whitespace and an optional lowercase `x` unit suffix. Require
NUL termination within 128 UTF-16 code units. Reject NaN, infinity, hexadecimal
numbers, commas, trailing garbage and conversion overflow/underflow. Range
validation applies to the finite parsed binary64 value before normalization;
this is not arbitrary-precision decimal validation. For example,
`32.000000000000000001` may round to 32 and be accepted. Reject negative nonzero
binary64 values, including subnormals, and canonicalize signed zero. Do not
silently clamp values outside the parsed range. Display finite numeric gain text
with `x` retained in the parameter's unit metadata. Sustain retains `Off`/`On`
labels and its existing normalized threshold. Command text uses the same strict
decimal grammar in normalized range 0..1, with no unit suffix and sufficient
digits for round-trip conversion. Do not give commands Off/On labels or
automatically reset their values. Text conversion does not execute commands.
Preserve floating-point rounding/flush controls; parser-library status flags
are not promised unchanged. Commands remain excluded from state serialization.

## Acceptance

1. Independent scalar ownership/audio comparisons cover all three variants,
   both host sample formats, channel sharing, sustain, retrigger ordering,
   repeated commands and partitioned blocks.
2. Malformed inputs, resource bounds, zero-frame flushes, pending recall and
   inactive output buses preserve the declared transaction rules.
3. Controller text tests reproduce and fix the baseline parser failure, cover
   complete input consumption and output preservation, and exercise all variants.
4. Existing core/host/model-state checks and actual module validators pass.
   Replay legacy audio and record the tested source, environment and any limits.
5. Update user-facing controls/build documentation and leave precise continuation
   notes. Agent counts and test totals do not replace criterion review.

## Public primary references

- [MIDI Association control-change table](https://midi.org/midi-1-0-control-change-messages)
  identifies CC123 as All Notes Off and CC120 as All Sound Off.
- [Roland FA-06/07/08 MIDI Implementation](https://static.roland.com/assets/media/pdf/FA-06_07_08_MIDI_Imple_eng01_W.pdf#page=5),
  version 1.01, June 1, 2017, sound-source reception pp. 4–5, distinguishes
  CC120 silencing from CC123 with retained Hold 1/Sostenuto sound. This is
  manufacturer practice; the shared pedal, mechanical state and filter-tail
  preservation above remain this project's explicit design contract.
- [Steinberg MIDI translation](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical%2BDocumentation/About%2BMIDI/Index.html)
  maps MIDI controllers to parameters and poly key pressure to its typed event.
- [Steinberg IMidiMapping](https://steinbergmedia.github.io/vst3_doc/vstinterfaces/classSteinberg_1_1Vst_1_1IMidiMapping.html)
  defines bus/channel-specific controller-to-parameter assignment.
- [Steinberg parameter flags](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical%2BDocumentation/Parameters%2BAutomation/Index.html)
  defines writable, read-only, hidden and automatable parameter behavior.
- [Steinberg PolyPressureEvent](https://steinbergmedia.github.io/vst3_doc/vstinterfaces/structSteinberg_1_1Vst_1_1PolyPressureEvent.html)
  specifies pressure, pitch and note-ID fields.

The pinned SDK source is the implementation compatibility reference. These
documents guide interoperability; they supply no instrument measurements.
