## Publication contract

The renderer inspects the final entry with `symlink_status` before rendering and
again before publication. Both live and dangling final symlinks are rejected,
including with `--force`; directories and other nonregular entries cannot be
forced. The renderer never opens the final destination for writing.

It exclusively reserves a randomly named sibling directory with
`create_directory`, allowing at most 128 collision attempts, and writes a temporary
regular WAV inside it. Both `flush()` and `close()` are explicitly checked before
publication. Rendering, stream, or pre-publication errors leave an existing output
untouched. Missing parents are rejected rather than created.

For a new destination, including an absent destination under `--force`,
`create_hard_link` publishes the completed file without replacing any existing
entry. This also refuses a file or symlink created after the preceding inspection.
If hard links are unavailable, publication fails safely; there is no direct-write,
copy, or overwrite fallback. An existing regular file under `--force` is replaced
with `filesystem::rename` on non-Windows hosts. The Windows branch uses
`MoveFileExW` with only `MOVEFILE_REPLACE_EXISTING`; it does not request a
cross-volume copy/delete fallback. The temporary location shares the destination's
parent filesystem.

These operations follow the [C++ filesystem operation contracts](https://eel.is/c++draft/fs.op.funcs)
and the [Windows move API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw).
The implementation assumes trusted, quiescent parent directories. The forced
regular-file check and replacement are separate operations: this is not an
adversarial ancestor or final-entry race sandbox. Default publication retains its
exclusive no-replace property at the final link operation.

Temporary cleanup removes only the known staged file and its containing directory.
Its destructor uses nonthrowing error reporting and emits a warning on failure;
after publication, that warning explicitly says the completed output was published
and does not change success to failure. This addresses the ambiguity described in
[A068](A068.md). Atomic visibility is distinct from power-loss durability: there
is no file/directory `fsync` guarantee, crash-recovery service, or preservation of
the replaced file's metadata.

## Observed verification

On Linux, the existing Release configuration used GNU C++ 14.2.0, CMake 4.4.5,
warnings as errors, and sanitizers disabled. These commands succeeded:

```sh
python3 tools/project.py validate
python3 tools/project.py sync --check
python3 tools/project.py next --json
cmake --build build/release --target rhodes_render --parallel 2
ctest --test-dir build/release -R '^cli\.(help|render|render_output|reject_nan|reject_unknown)$' --output-on-failure --no-tests=error --verbose
```

The selected CLI tests passed **5/5**. The new test uses CMake `execute_process`
and file operations, with no Python test/build dependency. At 48 kHz and 0.01
seconds, it independently compares all 58 header bytes and the 1,978-byte file
size: 480 binary32 samples, RIFF length 1,970, format tag 3, 18-byte extended
format with `cbSize=0`, mono/32-bit/four-byte alignment, byte rate 192,000,
`fact=480`, and 1,920 data bytes. It verifies the original file's SHA-256 remains
unchanged after refused overwrite, and forced replacement contains a complete
gain-zero render, allowing both IEEE signed-zero encodings.

It also verifies missing-parent refusal, directory preservation with and without
`--force`, and live/dangling final-symlink refusal in both modes while preserving
the link and target. Both symlink branches executed and passed on this host; the
test prints an explicit capability skip if another host cannot create a symlink.
No normal-run staging leftovers remained. Existing help, render, NaN-rejection,
and unknown-option checks also passed.

No broad suite, Windows/macOS build, sanitizer execution, forced I/O/close/cleanup
failure, concurrent attacker, or power-loss experiment was run. Error-path and
publication guarantees beyond the exercised cases are based on source inspection
and the API contracts, not claimed fault-injection results. Next: run this focused
test through normal Windows/macOS CI and keep those platform claims conditional
until observed.
