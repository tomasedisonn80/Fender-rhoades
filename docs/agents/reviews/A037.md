# A037 — Live parameters and lifecycle

**Observed contract.** The [implementation](../../../src/research_engine.cpp)
and [numerics](../../NUMERICS.md) agree: successful `prepare` rebuilds silent
modes and releases keys/pedal, even at an unchanged rate; successful modal
`configure` resets displacement/velocity. Rejection preserves prior state and
configuration. `set_decay` preserves coordinates and instantaneous mechanical
energy; note/pedal loss changes are immediate, without smoothing. Pickup/network
configuration immediately replaces coefficients, but the engine exposes neither
as live controls. Hard reset deliberately discards stored motion; musical release
does not.

**Energy boundary.** Coordinate continuity alone cannot make future structural
updates passive. For `E=(m*v*v+k*q*q)/2`, changing mass/stiffness at fixed state
changes energy by `(Delta_m*v*v+Delta_k*q*q)/2`. Record that parameter work or
define a justified migration. Moving pickup geometry additionally introduces
`-(partial_lambda/partial_p)*dp/dt`; the current voltage expression assumes fixed
coefficients. Smoothing needs specified physical quantities, valid domains,
durations, sample scheduling, and work accounting. Interpolating transition
matrices alone supplies no passivity guarantee.

**Required host contract.** Before calibrated assets, make the
[architecture's lifecycle requirement](../../ARCHITECTURE.md) concrete:

- One execution owner mutates runtime state. Prepare and validate versioned,
  immutable assets outside processing; prohibit concurrent configuration changes.
- While running, accept ordered sample-boundary note/pedal events and explicitly
  whitelisted controls. Today callers must split blocks at events. Define each
  future control's ramp and rejection policy before exposing automation.
- Rate, topology, or modal-normalization changes require deactivation followed
  by successful preparation and explicit reset. Validate a complete candidate
  before replacing the active engine; failure retains the previous instance.
- Any future seamless replacement needs a documented coordinate mapping,
  parameter-work accounting, switch boundary, old-asset lifetime, and error bounds.
  Preset restoration must explicitly select reset or supported migration.
