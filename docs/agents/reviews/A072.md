# A072 — Task acceptance and evidence relevance

**Scope:** Reviewed `AGENTS.md`, `tools/project.py`, `project/state.json`,
`docs/agents/STATE_FORMAT.md`, and `docs/VALIDATION.md`, plus their required
orientation documents. Canonical state remains unvalidated, with no completed
tasks or registered evidence.

**Finding:** `validate()` checks passing evidence-kind coverage, completed
dependencies, and immutable artifact hashes. Acceptance clauses are nonempty
strings, without a structured relationship to supporting records. This matches
the documented trust boundary: reviewers determine actual satisfaction. Hash
agreement and a `pass` label cannot establish experiment execution or scientific
adequacy.

**Concrete promotion risk:** An isolated `python3 -B` temporary-directory fixture
passed `validate()` with the same explicitly oscillator-only numerical record
attached to both `PHY-001` and `PHY-002`; `source_commit` was null. Canonical files
were untouched. Inspection of `complete` shows that this evidence reuse can pass
its gate once dependencies and ownership are satisfied, despite absent contact
coverage. By inspection, a single-note hardware-validation record could similarly
fill `KEY-001`'s required kind without demonstrating keyboard coverage. This is an
accidental relevance failure worth preventing, not a claim that arbitrary
repository edits defeat an authenticity guarantee.

Measured records have meaningful profile/session, held-out split, and measurement
reference checks. Fidelity never increases automatically; a separately reviewed
promotion requires the corresponding completed gate. Neither mechanism proves
the eight scientific obligations in `docs/VALIDATION.md`.

**Recommendation:** Before completion or fidelity promotion, require an explicit
reviewed mapping from stable acceptance identifiers to evidence and limitations.
Allow shared evidence with a relevance explanation. Bind that review to the
tested source/model/input snapshot: `source_commit` currently permits null and
otherwise checks syntax only. Reviewers must verify source applicability,
predeclared thresholds, condition coverage, provenance, failures, and scope.
These additions improve bookkeeping without promising attestation.

**Verification:** Focused source inspection and the isolated fixture only; no
broad tests or Git operations. Only this report was added.
