# A074 — Campaign integrity and isolated regression tests

## Scope and changes

Reviewed the operating contract, project overview/state/roadmap, the campaign
ledger format and generated index, `tools/campaign.py`, existing Python test
conventions, and [A069's generated-document review](A069.md). Added
`tests/python/test_campaign.py` using only the Python standard library. Its
synthetic assignments, reports, ledgers, and indexes live in temporary directories;
the real campaign is never loaded or mutated by the suite. The import is guarded
against accidentally invoking argument parsing or the CLI entry point.

Code review identified malformed JSON shapes and null task-name/scope fields that
could escape the CLI as `AttributeError`, an empty zero-request campaign that could
satisfy strict completion, Unicode digits accepted in IDs, and external report
trees reachable through symlinked ancestors. The integrator explicitly authorized
a narrow extension of ownership to `tools/campaign.py` before the source edit.

Validation now requires an object with an integer schema version, a requested
count in `1..999`, a list of complete assignment objects, ASCII IDs from `A001`
through the requested count, and unique well-formed `/root/` task paths. Scopes
must be nonempty strings. Running assignments require a null report hash;
completed assignments require a lowercase SHA-256 digest matching a regular,
nonsymlink report. Resolved report locations must stay within the campaign root
before report bytes are read. CLI commands and publication ordering are unchanged.

## Behavioral coverage

The 27 focused tests cover partial-ledger acceptance, strict rejection of 99
completed assignments or a remaining running assignment, and acceptance of an
isolated 100-completed-assignment fixture. That fixture is test data, not evidence
that any additional actual workers were launched.

Other cases exercise count/ID endpoints, excess assignments, duplicate IDs/task
names, malformed shapes/types/statuses/report paths, required fields, nested task
names, running/null and completed/hash consistency, and exact-byte report hashing.
Registration creates a running record; completion updates its hash and report
link; repeated completion with unchanged bytes is idempotent. A missing or unknown
member of a completion batch prevents all ledger publication. Completed-report
tampering is rejected by validation, registration, completion, and synchronization,
so `complete` cannot silently bless altered report bytes.

Rendering is checked for stable ID order regardless of input order, preserved
input data, escaped scope separators, correct totals, and a final newline. Stale
or missing generated indexes are detected and repaired without rewriting the
ledger. Fault injection verifies that a failed ledger replacement preserves the
previous files and cleans its temporary file. A failed index replacement after a
successful ledger replacement retains the committed assignment and old index;
`sync` recovers the index from the ledger. This is deliberately recovery across
two individually atomic replacements, not a two-file transaction. Report-file
symlinks and ancestors resolving outside the root are rejected; the external-path
fixture additionally fails if the implementation attempts to read those bytes.

## Trust and concurrency boundary

Task names and the requested worker count are supplied by the integrator. The
tool checks their form, uniqueness, internal counts, report existence, and byte
digests. It does not launch workers, authenticate collaboration results, establish
cryptographic agent/model identity, prove who authored a report, or verify that
reported experiments ran. The stored requested count remains a trusted assertion;
`--require-complete` checks against that assertion. SHA-256 detects a changed
report under an unchanged ledger digest; it does not authenticate the ledger.
One integrator must continue serializing campaign writes because the tool has no
multi-writer lock. Filesystem race attacks are outside this regression suite.

## Actual verification and handoff

Ran exactly this focused suite locally:

```sh
python3 -B -m unittest discover -s tests/python -p test_campaign.py -v
```

Result: **27 tests passed**, no skips, in 0.174 seconds. No full Python suite,
canonical campaign command, remote CI job, or hardware experiment was run by this
assignment. Changed paths are `tools/campaign.py`,
`tests/python/test_campaign.py`, and this report. No canonical ledger, task state,
Git staging, commit, or publication action was changed by this worker.
