## Confirmed finding — content scale omits resize notification when IPlugFrame is already set but native view is unattached

`PhotoEditor::setContentScaleFactor` (641–667) invokes host resizing only indirectly through `getFrame()->setZoom()`. `getFrame()` is the native VSTGUI CFrame, not the host IPlugFrame. When the host has called `IPlugView::setFrame()` before attachment, native `getFrame()` remains null: the setter changes `rect` and returns success without calling the available host frame.

The pinned public SDK `iplugviewcontentscalesupport.h` (39–53) permits scaling at any time the view is valid, requires successful handling to inform the host with `IPlugFrame::resizeView`, and explicitly describes direct `getSize` updating for the case **before IPlugFrame is set**. The present implementation treats both situations identically.

Exact public-interface probe sequence: create/initialize the actual direct controller from the existing bundle, create its editor, call `view.setFrame(&recordingFrame)`, query content-scale support, then `setContentScaleFactor(2.0F)`. The recording frame accepts resize requests by calling `view->onSize(size)`. It receives none. Command:

```
/home/agent/rhodes-7a7c13ab7da3/w2-004/scale_probe /home/agent/rhodes-7a7c13ab7da3/build-editor/VST3/Release/RhodesResearch.vst3
```

Exit 0; exact output:

```
result=0 resizeView_calls=0 size=2048x1536
```

The existing `scale_contract` never calls `setFrame`, so it cannot catch this distinction. Recommended bounded fix/test: when a host IPlugFrame exists, negotiate changed size via `resizeView` even before CFrame creation and commit geometry through the synchronous `onSize` contract; preserve the no-IPlugFrame path and verify refusal rollback. This is an SDK contract issue; no named-DAW failure is claimed.
