## Message and threading contract

`RhodesProcessor::notify` requires successful initialization and recognizes:

- `RhodesPhotoNoteV1`: integer `key` in 0..72, integer `down` equal to 0 or 1,
  and normalized binary64 `velocity` in 0..1.
- `RhodesPhotoReleaseV1`: no attributes; requests the queue's out-of-band release
  epoch, including when the ordinary command ring is full.

Null messages/IDs, unknown IDs, absent attribute lists, failed typed attribute
reads, invalid integers and invalid velocity encodings reject before changing
the queue or release epoch. The velocity path uses integer-bit validation and
round-to-nearest-even binary32 quantization. Negative subnormals, infinities,
quiet/signaling NaNs and values above one reject independently of DAZ/FTZ. Both
signed zeros canonicalize to positive zero. A valid command rejected by a full
queue follows worker015's emergency-release behavior.

The SDK's local `pluginterfaces/vst/ivstmessage.h` explicitly defines
`IConnectionPoint::notify` as a UI-thread, connected callback. The implementation
relies on exactly one serialized SDK/UI producer, as documented next to the
processor fields and notify implementation. It is not a general multi-producer
or reentrant endpoint, and it does not independently identify/reject foreign OS
threads. `notify` never inspects or changes the synthesis engine, MIDI tracker,
audio configuration, or UI-held flags.

The audio owner alone calls queue peek/apply/commit. A lifecycle callback may
assume that consumer ownership only while audio processing is stopped. Existing
host synchronization requirements remain in effect.

## Ownership, timing and transaction behavior

The processor keeps an independent fixed `array<bool, 73>` for photo-key
ownership. `ui_key_held(key)` is a read-only suspended/audio-owner diagnostic;
out-of-range queries return false. UI notes never consume the 256-entry MIDI
holder table.

Processing performs complete host syntax, parameter, MIDI ownership, dispatch
bound, cursor and fault preflight before peeking the audition queue. Therefore
any preflight rejection leaves queued commands, applied release epoch and held
UI keys untouched, along with the prior audio state.

After successful preflight, an accepted pending recall is installed first. The
audio owner then captures at most 256 queued commands, applies them directly at
the block boundary, and only afterward replaces `notes_` with the translated host
candidate. UI releases consequently consult MIDI ownership at the start of the
block, before future host events have occurred.

Each positive UI down strikes through the new bounded `press_key(key, velocity)`
audio-owner port, including repeated downs of an already held photo key. A UI up
or canonical zero-velocity down releases only its own UI flag. It calls the
physical release port only when no MIDI owner currently holds that key. The
zero-velocity special case deliberately avoids passing a physical zero-velocity
note-on through the core while another owner holds the key, because the core
defines note-on-zero as note-off.

The release epoch is checked after every command in the captured prefix. A new
epoch releases all currently UI-held keys in at most 73 steps; external MIDI
holders and shared sustain remain intact. This includes downs captured after a
focus/close release request, matching the queue's conservative release-wins
rule. New publications after the capture remain pending for a later block.

Host note-ons continue to retrigger normally. Physical host note-offs are
suppressed while the corresponding UI flag remains held, both in ordinary
rendering and in zero-frame CC123 flushes. MIDI ownership is still updated by
those host releases. This prevents either producer from releasing the other
producer's held key.

UI commands use direct audio-owner ports rather than the host dispatch array;
the existing maximum of 256 same-sample host actions remains unchanged. Each
block introduces at most 256 UI commands plus 73 emergency-release attempts.
There is no callback allocation, lock, retry loop or UI/window/file access in
the added path.

Queue commit and applied-epoch update occur only after the accepted render or
zero-frame flush succeeds. An accepted arithmetic failure may already have
changed mechanics/held flags, consistently with the processor's existing
accepted-fault policy; it does not roll back audio. The prefix and epoch remain
uncommitted, subsequent processing is fenced, and an explicit reset discards
the stale prefix before recovery. A failed internal commit also faults the
adapter instead of allowing replay.

## Zero frames, history and lifecycle

Valid zero-frame calls deliberately process UI commands and emergency releases.
They do not advance the frame cursor or render/clear mechanical, FIR or panel
effect history. A strike adds its normal impulse; a release changes damping.
This allows a host's parameter/event flush boundary to service editor key-ups
without advancing audio.

The new `BasicEventProcessor::press_key` validates key and binary64 normalized
velocity, calls the underlying engine's note-on, and leaves the cursor/history
intact. Invalid arguments are inert. An unexpected valid engine failure sets
the existing fault fence, just as the parallel release port does.

Accepted state recall and host lifecycle reset preserve their existing full
engine/MIDI reset behavior. They additionally clear UI-held flags and discard
one currently published queue prefix. A UI command published after that discard
capture remains queued. The reset does not alter producer counters or reset the
applied epoch: a still-unacknowledged release conservatively clears the next
captured batch. A successful normal transaction acknowledges that epoch, after
which later downs work normally. No UI focus/close/overflow command invokes a
MIDI panic or resets shared sustain.
