# W2-012 — bounded front-panel effects cost review

**Scope:** HOST-004 review only; no repository, Git, canonical-state, or production-code changes. Read the operating contract and required project context.

**Finding:** `FrontPanelEffects::process/update_targets` has fixed storage and no source-level loops, allocation, locks, or I/O. Its per-frame upper call count is two `pow`, one `sin`, two shelf updates, and four ramp advances; `tan` runs in preparation. Fixed controls avoid `pow`. Neutral settled controls also avoid shelves and `sin`. This is a structural operation bound, not a wall-time bound for libc or the scheduler.

`RhodesProcessor::render` interpolates/quantizes the four continuous panel controls each frame and calls the effects once after monitoring gain and before mono folding/expression. Consequently, sparse host automation points can still cause new tone targets—and two `pow` calls—on successive frames.

**One measurement:** six cases, 1,000,000 frames each, one invocation; precomputed finite input in [-0.125, 0.125), normalized controls, active vibrato in both active cases. Automation changes bass/treble/intensity/speed every frame; tone values avoid neutral. Preparation, allocation, and input/control generation are excluded; loads and an asymmetric stereo checksum are included. All six checksums were finite and fault latches clear; exit 0.

Values are wall-clock means; thread-CPU means differed by <0.03 ns/frame. Automated cost was about 2.9–3.7× active fixed. Single observations do not establish rate-dependent scaling, worst-case timing, complete-processor cost, device deadlines, or denormal-tail behavior. No optimization is proposed from this capture alone.
