## Controller and PhotoView behavior

Controller API for integration:

```cpp
using AuditionOwner = std::uint64_t;
static constexpr std::size_t kMaximumAuditionOwners = 32;
AuditionOwner registerAuditionOwner();
bool unregisterAuditionOwner(AuditionOwner owner);
int heldAuditionKey(AuditionOwner owner) const noexcept;
bool auditionNote(AuditionOwner owner, int key, bool down, float velocity);
bool releaseAuditionNotes();       // explicit global emergency only
bool retryAuditionRelease();       // sends nothing when no emergency is pending
```

All operations are serialized UI-thread operations. The controller contains 32 fixed owner slots, each holding one token and one key; a bounded scan determines whether a key still has another owner. Registry operations allocate no additional storage. SDK message allocation remains on the UI thread, as before. The processor ABI, message identifiers/attributes, audio storage and parameter collection are unchanged.

Token zero means unavailable/invalid. Full registration returns zero without disturbing current owners. Successful registrations use monotonically increasing uint64 tokens. Counter wrap reaches zero and permanently refuses further registrations; freeing slots cannot revive an old token. Controller termination revokes owners, and reinitialization does not reset the token counter. A narrowly scoped private friend enables the regression test to reach the otherwise impractical uint64 boundary; it adds no host/editor-facing setter.

Each valid down can restrike the key. An up clears only its owner's matching key, and emits an ordered V1 up only when no other owner remains. Repeated or mismatched releases are harmless. A down on a different key first releases that owner's previous key. Both signed zero down velocities normalize to scoped up **before** ownership aggregation, matching processor semantics. Positive binary32 subnormals are widened with `control::widen`, so DAZ does not silently turn a genuine down into a zero-velocity wire release.

PhotoView acquires its token at construction and revokes it at destruction. It retains ordinary note-up cleanup on cancellation, mouse-up, focus loss, removal and close. A failed release stops the corresponding new click or glissando transition rather than appending a new down to that failed transition. The view's idle callback checks the controller's held-key query and clears its held highlight/drag state after a global emergency canceled another view's ownership.

## Failure and recovery boundary

A failed SDK allocation, missing attribute list, rejected attribute write, or rejected send invokes the existing global emergency release. The controller clears all owner key states to reflect V1's global failure policy. If emergency allocation or delivery also fails, cleanup remains pending. Idle callbacks, owner teardown and controller termination retry it. A down while pending attempts recovery and returns false even when that retry succeeds; that recovery call never appends a fresh down. A failed cleanup is observable through a false return value, and the final owner can be revoked without forgetting the pending emergency.

The existing processor emergency remains out-of-band and wins the complete captured audio prefix. This patch does **not** add audio-side acknowledgement. Consequently, a later, separate UI down issued before the processor consumes a successfully sent emergency can still be canceled by that emergency's snapshot. The normal path no longer sends an emergency, removing the ordinary-click race. Recovery from an actual transport failure remains a global fail-safe event, not a promise of immediately audible retrigger or failure isolation between views. Persistent host transport failure cannot guarantee delivery; retries preserve the cleanup request while a usable connection exists.

## Regression fixture

The new test implements a fixed-lifetime SDK IHostApplication, IMessage/IAttributeList, and recording IConnectionPoint. It captures actual messages emitted by RhodesController and compares literal message IDs, attribute names, keys, velocities and order. It does not reproduce the processor queue implementation or derive expected wire fields from production constants.

The final fixture passes **392 checks** per compiled model configuration. Cases cover:

- Fresh cancellation/down emits only one down, with no preceding or follow-up global release.
- Idle service and repeated idle sibling close preserve the other view's held key.
- Explicit and automatic key transitions produce FIFO up/down sequences; repeated down can restrike.
- Same-key two-owner release waits for the last owner; distinct keys close independently.
- Stale tokens after slot reuse cannot affect live owners; malformed key/velocity/zero-owner requests preserve current ownership.
- A literal 32-owner capacity, failed 33rd registration, free-slot recovery, and held-note cleanup at capacity.
- Runtime uint64 terminal-token and wrap-to-zero tests, including cleanup of a held final-token owner.
- Both positive and negative zero down velocities obey the last-owner rule.
- Smallest positive binary32 subnormal remains an actual down on the wire under DAZ/FTZ where SSE is available.
- Note send, allocation, attribute-list, and each typed attribute-write failure invoke global emergency and clear all held-key queries.
- Failed down also clears other owners; repeated failed emergency sends remain pending, and a successful recovery attempt emits no down.
- Failed final-owner cleanup retains an emergency for retry.
- Controller termination releases shared held keys once, with no idle global panic; reinitialization preserves stale-token isolation.

This fixture validates controller-to-SDK traffic and controller ownership. It does not attach a native window, call PhotoView through native input, render audio, or establish DAW behavior. Parent/native tests remain responsible for that evidence.
