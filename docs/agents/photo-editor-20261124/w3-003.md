## Changes and causal evidence

Owned production changes are only `plugins/vst3/photo_native_focus.cpp` and `.hpp`. At the parent's later request, the complete standalone fixture was preserved as `tests/cpp/photo_native_focus_test.cpp`; it is not registered with CMake yet. This worker made no SDK, host, view, canonical-state or Git changes.

The retained W2 tree is root → floating host → embedding container → editor. The cold focus destination is the editor's grandparent, not its immediate parent. The [X11 protocol](https://xorg.freedesktop.org/releases/current/doc/xproto/x11protocol.html) defines an upward focus transfer as Ancestor FocusOut on the old focus, Virtual FocusOut through intermediate ancestors, then Inferior FocusIn on the destination. [XEmbed](https://specifications.freedesktop.org/xembed/latest-single/) distinguishes logical widget focus from actual X focus; ordinary toolkits may retain X focus on a top-level window, while its formal FocusProxy can be a separate non-ancestor window. The implementation covers the observed ancestor handoff only.

The observer caches the immediate embedder and, after at most three QueryTree requests, its immediate parent only when that parent is directly under root. It observes those exact windows on its existing private XCB connection. A one-shot exception requires child Pointer FocusOut → normal Nonlinear FocusIn → normal Ancestor FocusOut, completed by the matching Inferior FocusIn on the cached destination. Ordinary ancestor departures, external departures, and out/back sequences still cancel. Once accepted, the exact host focus target is monitored for subsequent loss. A return into the editor must be confirmed by its FocusIn. The 64-event budget and conservative overflow behavior remain; resolving an incomplete event pair can use one additional UI-thread ordering reply.

Two intermediate assumptions were disproved and corrected. Attachment can occur while a startup window owns focus, so acquisition is recognized from events rather than an attachment-time focus snapshot. More significantly, the task-local XCB tracing interposer observed:

```text
40386.727074 tree: editor parent=4194376, root=543
40386.727104 tree: container parent=543
40386.769683 REPARENT: container 4194376 → floating host 4194377
```

The initial implementation permanently invalidated its cached topology at that reparent, before the first gesture. It now cancels immediately, marks that known reparent, and refreshes once on the next same-window attachment call. DestroyNotify does not request a refresh, avoiding repeated attempts on a stale native handle. The complete 52-line causal record is `worklogs/w3-003-reparent-causal-trace.log`; the diagnostic source and full run remain alongside it. The trace also showed acquisition and ancestor transfer in successive idle drains, with no synchronized fence between them.

## Limits and handoff

This qualifies the recorded bare-Xvfb topology without a window manager. A reparenting desktop WM may insert another frame above the host top; the bounded two-level rule does not qualify that topology. Raw hierarchy does not establish logical focus for arbitrary docked hosts. There is no desktop-wide REAPER, Wayland, Windows or macOS claim. Request counts are bounded, but synchronous server reply latency is not time bounded. SDK tests do not process audio; REAPER audio was closed, and direct REAPER endEdit callbacks and processor note-off were unobserved.
