# W2-013 — Native Linux focus loss cancellation

## Outcome

The corrected actual direct VST3 photo editor passes **27/27 checks** in the unchanged native harness and **20/20 checks** in the supplemental held-motion probe. The separate XCB observer test passes **21/21 cases** on real Xvfb. Both native editor runs exited 0; all recorded source and binary inputs remained unchanged during each run.

A genuine native FocusOut now ends a held Volume gesture before pointer release and clears a held photographed key. Pointer movement while the button remains held cannot continue editing after the loss, and restoring focus without a new press cannot resume that gesture. A rapid out/back transition still cancels. Focus into a native descendant preserves the active drag.

All 1,769,472 decoded RGB pixels of the full 1536 × 1152 photograph match the reference exactly before and after interaction. The keyboard-focus-loss capture is also exactly the reference. I visually inspected the final held-key and Volume focus-loss images; neither retained the held overlay.

## Root cause and public integration point

In the pinned SDK, `vstgui4/vstgui/lib/platform/linux/x11frame.cpp` defines `Frame::Impl::onEvent(xcb_focus_in_event_t&)` as an empty handler for raw FocusIn/FocusOut. Its XEmbed client-message path forwards activation to CFrame, explaining why the direct XEMBED_WINDOW_DEACTIVATE probe worked while actual XSetInputFocus loss did not cancel.

The public `CFrame::getPlatformFrame()` and `IPlatformFrame::getPlatformType()` / `getPlatformRepresentation()` provide the X11 child ID. There is no public raw-event listener hook there. The implementation uses those public hooks and never replaces VSTGUI's private single-window event handler.

## Implementation decisions

Each PhotoView owns one independent XCB connection, subscribed only to FocusChange on its native child. X11 event masks are per client, so this preserves the SDK's own mask and queue. The observer is reset on removal and destroyed with the view.

The existing idle hook drains at most 64 events. Before a new left-button interaction, old loss events are discarded; before an active pointer move, a get-input-focus round trip orders pending events on the independent connection, then the bounded drain runs before any value change. The query's returned focus value is not used as the decision, so leaving and returning between polls still counts as a loss.

| Native transition | Handling |
| --- | --- |
| Genuine FocusOut outside the native editor subtree | Existing `cancel_interaction()` ends the edit and releases the key. |
| FocusOut NotifyInferior | Preserved: focus moved into a native descendant. |
| FocusOut NotifyPointer | Ignored pointer-focus bookkeeping, including the first click assigning explicit focus from PointerRoot. |
| NotifyGrab / NotifyUngrab | Preserved: popup keyboard grabs alone do not change actual input focus. |
| Actual focus change while keyboard is grabbed | Cancels; NotifyWhileGrabbed is not ignored. |
| 64-event drain budget exhausted | Conservatively cancels and continues draining on a later idle. |
| Mid-observation connection failure | Cancels once and disables the observer until native reattachment. |
| Initial attachment error | Leaves existing host/VSTGUI focus hooks active; no idle reconnection loop. |

All connection and query work is on GUI callbacks. This makes no audio-thread I/O changes and creates no window or visual overlay. The event-loop work is bounded by count; synchronous X11 reply latency still depends on the X server. A real server-disconnection fault was not injected into the running host.
