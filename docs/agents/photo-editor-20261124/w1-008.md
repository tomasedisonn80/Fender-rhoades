## Added API

- `include/rhodes/front_panel_state.hpp`: `FrontPanelState` with bass/treble/speed defaults 0.5, intensity default 0, and vibrato default false. `valid_front_panel_state` accepts normalized binary32 controls, including negative zero and positive subnormals; `neutral_front_panel_state` checks exact persisted defaults using canonical integer bits. Inactive but nondefault speed/intensity values are still saved.
- `include/rhodes/plugin_state.hpp`: `PluginState { InstrumentState instrument; FrontPanelState panel; }`, `valid_plugin_state`, `plugin_state_v3_bytes = 40`, `EncodedPluginStateV3`, `encode_plugin_state_v3`, `decode_plugin_state`, and adaptive `encode_plugin_state`.
- The adaptive result is `EncodedPluginState { bytes[40], size }` with mutable/const `view()` spans. At exact panel defaults it produces the unchanged 16-byte v1 representation for unity expression or unchanged 20-byte v2 representation otherwise; any other valid panel configuration produces 40-byte v3.
- `decode_plugin_state` accepts only exact 16/20/40-byte packets with matching versions and immutable model IDs 1/2/3. Legacy packets acquire the default neutral panel. V3 retains header and v2 instrument offsets, adding bass at byte 20, treble 24, intensity 28, speed 32, and binary32 vibrato 36. Boolean fields accept only exact positive/negative zero or unity; saved zeros are canonical positive zero. Invalid fields, models, headers, or version/length combinations are rejected.
- Existing `InstrumentState`, codecs, and `StateMailbox` are untouched. The parent accepted these new API names and adaptive-result shape before implementation.

## Mailbox implementation and bounds

`PluginStateMailbox` keeps eight atomic 32-bit words and one atomic 64-bit guard. Both employed atomic widths are statically required to be always lock-free. Guard bit 0 is temporary writer ownership; bit 1 is pending recall; upper 62 bits are the monotonic revision. Every successful begin, recall, and end advances revision, including identical-value recalls. All guard and payload operations are sequentially consistent.

`begin_block` loads the guard, immediately rejects busy/exhausted state, and makes at most one strong CAS. Once owned, it copies exactly eight atomic words and publishes a fresh stable revision. Pending remains set. The returned token has the same public member shape as the legacy token: `publication_token`, `recalled`, `apply_recall`, and `may_publish`.

`end_block` validates the complete state before acquisition, makes at most one strong CAS against that exact token revision, stores exactly eight words after success, then publishes the next revision with pending cleared. Invalid input does not alter its token or consume pending. No ownership survives either call. `abort_block` is intentionally a no-op because begin never consumes pending.

Only non-audio `request_recall` and `snapshot` may retry. A successful snapshot sees equal stable guards bracketing atomic payload reads. Sequential consistency and no revision reuse prevent a snapshot from straddling a writer. No shared ordinary floats, heap allocation, mutex, callback, yield, sleep, or retrying snapshot call appears on either audio path.

Revision exhaustion fails closed without wrap or reset and retains a readable final snapshot. A begin using the final available revision may return a selected recall whose end fails due to exhaustion; its pending data remains intact. A private friend declaration for `plugin_state_detail::MailboxTestAccess` supports deterministic standalone busy/exhaustion tests. Only the test defines this friend; production has no public reset, runtime test mode, or additional branch.
