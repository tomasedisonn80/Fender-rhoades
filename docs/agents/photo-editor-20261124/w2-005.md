# Wave 2 worker 005 — UI audition ownership audit

Date: 2026-11-24. Parent task: HOST-004. Bounded read-only implementation review; no repository, Git, claim, canonical state, production source or test modifications. Only this external report was written. No native app interaction or executable test was run in this audit. Findings below are source-level execution traces, not claims of measured playback.

## Findings

### 1. Ordinary left mouse-down can immediately release its own new audition

`plugins/vst3/photo_editor.cpp:112-139`: `onMouseDownEvent` calls `cancel_interaction()` before hit testing. At lines 289-298 that function always calls `controller_.releaseAuditionNotes()`, even when `held_key_ == -1`. A keyboard hit then calls `move_audition()`, which sends the down message.

`plugins/vst3/controller.cpp:193-216` sends an SDK `IMessage` named `RhodesPhotoReleaseV1` and then `RhodesPhotoNoteV1`. `plugins/vst3/processor.cpp:146-179` translates release into a release epoch and down into a queued command. `apply_editor_audition` at lines 204-235 applies all captured commands, then globally releases every UI-held key when the epoch changed. `include/rhodes/editor_audition.hpp:88-111` captures epoch before the write cursor, so the snapshot legitimately includes both the preceding release and following down.

Deterministic source-level repro: start with no UI ownership and old applied epoch; call a left mouse-down hitting key 40; do not process between the two SDK notifications; process one accepted block. The down is applied then immediately released by the epoch, leaving `ui_held_[40] == false` while the PhotoView's `held_key_ == 40`. This is a normal single-view bug, not dependent on supporting independent simultaneous views. If the audio thread happens to consume the release before the down it does not occur, making the behavior scheduling-dependent.

### 2. A view can release another view's UI notes

`PhotoView::cancel_interaction` unconditionally uses a controller-wide panic. It is invoked on new left clicks, mouse cancellation, focus loss, window deactivation, removal and destruction. `PhotoEditor::onFocus(false)` at lines 546-550 additionally sends the same panic when it has no PhotoView. `willClose` at lines 575-578 sends it even after view cancellation; `close` at lines 605-608 sends it with no frame.

Source-level repro: one initialized controller C has editors A and B; A has an accepted audition down for key 40, followed by an accepted processing block. Call B's public `IPlugView::onFocus(false)` while B is unattached (the test suite explicitly exercises this call as safe), then process another accepted block. B's no-view branch sends `RhodesPhotoReleaseV1`, which releases A's UI ownership. No B note or native parent is needed. With attached B, closing or cancelling B follows the same global release path. Clicking any control in idle B also follows that path. Creating a second view alone and `onFocus(true)` alone do not explicitly send release in the inspected production code; actual host focus switching may legitimately deactivate A, which should release A's own notes. Do not describe mere creation or focus gain as an unconditional demonstrated release.

### 3. Same-key ownership cannot distinguish views

`plugins/vst3/processor.hpp:114-115` stores one queue and `std::array<bool, key_count> ui_held_` per processor. `EditorAuditionCommand` has only key/down/velocity. `RhodesPhotoNoteV1` likewise has no owner attribute. Even if unconditional global releases are removed, A-down(40), B-down(40), A-up(40) releases B's key too. Per-view `held_key_` does not solve shared-key ownership.

## Scope distinction

`tests/cpp/vst3_photo_editor_test.cpp:92-128` explicitly keeps two distinct simultaneous IPlugViews for one controller. It establishes creation/interface support, but the file says no view is attached; its focus checks at lines 178-179 check return codes and geometry, not audible ownership. It does not establish independent audition semantics.

`tests/cpp/vst3_editor_audition_test.cpp:466-492` uses two separate ProcessorHost/processor instances and verifies second-instance release cannot clear the first instance. That isolation remains true: no shared/static queue was found. It cannot cover two views connected through one controller to one processor.

The specification evidence inspected does not explicitly demand polyphonic independent audition across multiple views. Nonetheless, an idle or unattached second view clearing another view's note is a concrete lifecycle side effect; the ordinary mouse-down self-release is unambiguously wrong under the existing single-view keyboard contract.

## Minimal fixes and SDK compatibility

1. Immediate minimal correction: remove unconditional `releaseAuditionNotes()` from normal `cancel_interaction`, idle/unattached focus and close paths. Keep `release_key()` as the normal, ordered key-up operation. Remove the duplicate global panic from `willClose`; lifecycle handling should release only the state owned by that editor. Retain a global emergency release for an actual failed/dropped release or transport overflow, and processor lifecycle reset. Merely guarding the global call with `held_key_ >= 0` is insufficient: on retrigger/glissando a prior release epoch followed by a new down in the same captured batch can still kill the new note. Normal transitions must use FIFO note-up/down commands.

2. To support independent views robustly, add view ownership rather than claiming that step 1 alone provides it. Smallest normal-path change retaining existing SDK wire format: a controller UI-thread audition registry keyed by a stable per-editor token, with per-key holder counts. A view submits token plus its current key; controller sends existing V1 note-up only when the last owner of that key releases, and never sends global panic for an idle token. A new accepted down can still restrike the physical key. Token allocation/revocation must be controller-owned, stale cancellation must be ignored, and delivery failure must clear/reconcile the registry because existing queue overflow intentionally panics all UI ownership. Define that shared transport failure clears all audition owners; do not promise failure isolation with V1. This adds no non-SDK pointer to messages and no audio-thread allocation.

3. If per-view failure isolation is required, use a versioned SDK message with an integer owner token (`IAttributeList::setInt/getInt`) and bounded audio-owned owner bookkeeping. Scoped release must travel with the token; aggregate physical release occurs only when no UI owner and no MIDI holder remain. Use bounded owner slots plus generation/token validation so a stale close cannot release a reused slot. Queue overflow/release accounting must carry scoped release information or explicitly retain documented global emergency behavior. This is broader than the minimal lifecycle fix and needs a reviewed bound/capacity policy. Do not send a GUI pointer across the processor connection.

An alternative is an explicit single active audition owner per controller, with token-checked release and deterministic transfer on a new owner's down. That is smaller than multi-owner storage, but represents exclusive audition semantics and must be documented/tested as such; it does not satisfy independent simultaneous held notes.

## Targeted regression tests to add

- Native/controller message sink test: fresh keyboard mouse-down must not send a global release first; feed its actual emitted message sequence into the processor without an intervening block and assert held ownership after processing.
- Two views on one connected controller: A holds key; B unattached `onFocus(false)`, idle close/removal, or control click does not clear A. A's own focus loss/close releases A.
- Sequence independent of callback cadence: old-key up then new-key down before one process call leaves new key held, including repeat click on the same key.
- For independent-view policy: A/B hold different keys; close A leaves B. A/B hold the same key; release A leaves B; release last owner releases physical key. Keep external MIDI ownership tests.
- If registry/tokens are added: repeated cancel is idempotent; stale token after close/reopen has no effect; failed message/overflow behavior follows the declared global emergency policy without stuck ownership. Run all model variants where processor logic is shared.
