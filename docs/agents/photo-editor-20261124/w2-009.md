# W2-009 — bounded REAPER native parameter and focus qualification

Parent task: HOST-004. Date: 2026-11-24. Scope: one isolated real-DAW probe;
no Git, canonical-state, SDK, production-source, or shared-build changes.

## Result

**Native control-to-host parameter mapping passed for the Filtered instrument.**
Actual XTEST pointer gestures in its photographed editor changed REAPER's
`TrackFX_GetParamNormalized` values at precisely indices 0, 1 and 19–23. All
seven photographed feedback readouts were visually inspected and matched
REAPER's formatted values.

**Native focus-loss cancellation failed in the tested Linux X11 path.** Moving
native input focus from the plug-in child to the actual REAPER main window
produced an observed `FocusOut` on the native child, but a still-held Volume
drag continued changing the host parameter. A held photographed key remained
visually held after the same focus transfer. Both pre-loss/post-loss image
pairs were pixel-identical. Pointer release subsequently cleared the feedback.

This is one bounded REAPER 7.86 run with the audio device closed. It does not
establish audio-device operation, audible audition, processor-side note release,
automation recording, direct VST3 edit-callback balancing, or other platforms.

## Observed parameter mapping and native edits

Each gesture changed only the indicated index among all 27 recorded values.
The values while held and after release matched. Continuous values matched the
independently expected gesture deltas within an absolute tolerance of `2e-5`.
The full-precision strings below were also visible in the native feedback.

| Photographed control | REAPER index | Observed identifying string | Normalized before → after | Host/native formatted feedback after |
| --- | ---: | --- | --- | --- |
| Volume / Monitoring Gain | 0 | `0:0` | `0.5 → 0.699999988079071` | `22.399999618530273` |
| Pedal / Sustain | 1 | `1:1` | `0 → 1` | `On` |
| Bass | 19 | `19:3` | `0.5 → 0.791262149810791` | `6.9902915954589844 dB` |
| Treble | 20 | `20:4` | `0.5 → 0.791262149810791` | `6.9902915954589844 dB` |
| Intensity | 21 | `21:5` | `0 → 0.20000000298023224` | `0.20000000298023224 x` |

| Vibrato | 23 | `23:7` | `0 → 1` | `On` |

Volume, Intensity and Speed each moved upward by 36 original-image pixels,
equivalent to 24 native pixels and an expected normalized delta of 0.2. Bass
and Treble each moved 30 source pixels right, giving `30/103` normalized travel.
The pedal and Vibrato each switched from Off to On.

The remaining enumeration resolves the W2-008 parameter-count ambiguity:
indices 0–23 are the 24 native parameters; REAPER additionally returns Bypass
at 24 (`24:bypass`), Wet at 25 (`25:wet`) and Delta at 26 (`26:delta`). Expression
is index 2, while indices 3–18 are the sixteen channel-specific All Notes Off
parameters with IDs 4096–4111. This run did not exercise those controls.

### Preserved harness assertion correction

The initial harness incorrectly expected `TrackFX_GetParamIdent` to return bare
VST3 IDs such as `0` and `3`. Actual REAPER output was `0:0` and `19:3`, and
analogously `index:ID` for the other native controls. Consequently the seven
`parameter_identity_*` rows in the raw transcript and `run.json` say `fail` even
though their accompanying observed names and identifiers contain the intended
mapping. Those files were preserved unchanged. `analysis.json` records the
explicit correction and rechecks the retained observations; no host run was
repeated and no product result was silently rewritten. The seven native gesture
checks themselves passed in the original run.

## Native focus-loss failure

The runner established native child input focus in bare Xvfb and used ordinary
XTEST pointer press/move events. While the left button remained held, it called
XSetInputFocus on REAPER's actual main window. It did not send a fabricated
FocusOut or inject XEmbed activation/deactivation messages.

The X server delivered `FocusOut` to child `6291457` with `mode=0` and
`detail=3`; the floating parent `4194383` also received `FocusOut`, and REAPER
main `4194360` received `FocusIn`. The same native event sequence was observed
for the separate held-key probe.

| Observation | Actual result |
| --- | --- |
| Volume before native focus loss, after an additional upward drag | `0.800000011920929` |
| Volume immediately after focus loss, before button release | `0.800000011920929` |
| Volume after another 18-source-pixel upward movement, still held and still unfocused | `0.9000000357627869` |
| Volume held image versus image after focus loss | Exactly identical RGB, all 786,432 pixels |
| Keyboard MIDI 60 held image versus image after focus loss | Exactly identical RGB, all 786,432 pixels |
| Keyboard image after focus loss versus idle | 15,175 pixels differ; held highlight and popup visibly persist |
| Final image after pointer release and moving outside versus idle | Exactly identical RGB |

The additional host parameter change proves that this native focus transfer did
not cancel the active drag. The images independently establish uncleared held
feedback. ReaScript did not expose the plug-in's `beginEdit`/`endEdit` callbacks,
so this worker cannot directly count callback balancing or say whether an
isolated `endEdit` callback occurred. The observed interaction behavior fails
the intended focus-loss cancellation boundary regardless of that unobserved
callback detail.

**Actionable handoff:** route the real Linux native focus/deactivation path into
the editor's cancellation logic, then repeat this bounded held-Volume and
held-key case against the newly built module. Preserve the distinction between
native FocusOut, an explicit XEmbed protocol probe, and direct host onFocus
callbacks. A desktop run with a normal window manager remains a separate check.
