## Smallest useful API and behavior

1. **Two factory classes.** Derive the processor from `Vst::AudioEffect` and the
   controller from `Vst::EditController`; assign fresh, permanent class IDs.
   Register the processor as an instrument/synth. Export no custom editor:
   `createView()` returns null. The controller still defines ordinary parameters
   and conversions for the host's generic editor. Keep SDK headers out of the core.
2. **Buses and samples.** No audio input; one main mono audio output; one event
   input. Initially declare one input channel, VST channel index 0, and document
   that restriction. Accept only MIDI 28..100 and map without octave-name
   assumptions. Other pitches/types/channels are explicitly unsupported and
   ignored. Support 32-bit host buffers through fixed double scratch storage;
   64-bit output is inexpensive to add but must be explicitly advertised/tested.
   Validate requested arrangements and sample size. Report zero added latency
   and `kInfiniteTail` until a justified finite tail cutoff exists.
3. **Only two parameters.** Stable IDs for `Monitoring gain` and `Sustain`.
   Gain is an explicit conversion from modeled volts to host sample units, with
   finite bounded range and a documented default, not a calibrated Stage volume
   pot. Sustain is discrete (`stepCount=1`), default up, normalized threshold
   `>=0.5`. This reproduces MIDI CC64's 0..63/64..127 distinction for values
   normalized by 127; it does not implement half-pedal mechanics. Do not expose
   synthetic mass, pickup geometry, or other structural constants as live knobs.
4. **MIDI mapping.** Implement controller `IMidiMapping::getMidiControllerAssignment`
   for bus 0/channel 0/`kCtrlSustainOnOff` (64) to the sustain ParamID; return
   false for other mappings. VST3 sends CC functionality as ordinary parameter
   changes, not generic incoming raw CC events. `kLegacyMIDICCOutEvent` is not an
   input-CC solution. The newer optional `IMidiMapping2` replaces this interface,
   but its documented fallback permits the smaller MIDI-1-only first adapter.
5. **Repeated notes.** One physical state per pitch remains mandatory. Freeze a
   note-ownership rule before coding: a small initial policy is latest note ID
   owns key-down; an earlier ID's note-off cannot release the newer strike.
   `noteId==-1` falls back to the documented pitch-based rule. Retrigger adds
   excitation without resetting motion. Preserve the existing zero-intensity
   release convention explicitly; do not silently claim arbitrary overlapping
   MIDI voices or note-expression support.

## Timing, lifecycle, and state hazards

- `ProcessData::inputEvents` and `inputParameterChanges` are separate streams.
  Collect and validate all supported note events and parameter points within
  fixed capacity before mutating the engine. Preserve source order within each
  stream. Define the missing cross-stream tie rule, for example parameters before
  notes at equal offsets, then assign producer sequence numbers for the bounded
  adapter. Do not reorder equal-time note-off/retrigger pairs by event type.
  Steinberg's retrieved interfaces do not supply a shared global sequence number.
- Apply events before observing their sample. Offsets must satisfy the core
  adapter contract `0 <= offset < N`; offset `N` is not an in-block event.
  Count parameter points against the work budget too. Bound raw host-list
  traversal, including ignored entries, so an unlimited list cannot cause
  unlimited callback work. Never silently truncate a release on overflow.
- Continuous gain automation is a piecewise-linear curve: process all points,
  retain the prior value at implicit offset -1, and interpolate in normalized
  space. A final-point-only shortcut loses timing. Discrete sustain changes use
  their point offsets. Test the mixed pedal/note tie rule independently.
- Prepare and allocate outside `process()` and `setProcessing()`. Reject rates
  outside the engine domain. Initially reject `maxSamplesPerBlock` above the
  adapter's frozen maximum in `setupProcessing()`; larger-block segmentation is
  a separately specified extension. Clear every writable rejected output and
  return an error/status without advancing mechanics on input rejection.
- Handle null event/parameter pointers, inactive buses, zero-frame calls, and
  parameter-only flush calls. A flush updates validated parameter state without
  advancing the physical engine; do not feed zero-frame events into the bounded
  audio adapter. Do not dereference absent audio buffers. Set silence flags from
  the written output, not merely from the absence of note events.
- Arithmetic failure is distinct from input rejection: latch reset-required,
  silence subsequent processing, and recover only through a declared lifecycle
  reset. No callback logging, allocation, locks, file access, or UI mutation.
- Save a small versioned configuration using explicit byte order and fields
  (magic/version/model ID/gain/sustain). Validate a complete temporary state
  before committing. Implement processor `getState/setState` and controller
  `setComponentState` with the same decoder. Restore configuration at equilibrium,
  clearing note ownership; ringing mechanics are not a checkpoint feature.
  Handle active-state recall through a bounded ownership/publication protocol,
  rather than letting UI-thread `setState` race audio-thread engine mutation.
  Controller state has no separate UI payload. Unsupported versions, NaN,
  truncation, or invalid values must leave prior configuration intact.

## Headless Linux build plan

Official current support lists Ubuntu 24.04 x86_64/GCC 13.3+. The older setup page
still mentions Ubuntu 22.04 and a broad GUI-example package list; do not confuse
that list with a requirement for an editor-free module. Use CMake **3.25+** for
the pinned SDK, a C++20 compiler, ordinary C/C++ development libraries, and
Make or Ninja. The core's default build can retain its existing CMake minimum.

Add `RHODES_BUILD_VST3=OFF` and `RHODES_VST3_SDK_ROOT` cache options. Under the opt-in
branch, configure the SDK with plugin examples, hosting examples, VSTGUI, Wayland,
and automatic plugin links disabled. Keep utilities/module metadata and validator
enabled. Add the supplied SDK directory, then `smtg_add_vst3plugin` for the adapter;
link `sdk` and `rhodes_core`, and set `POSITION_INDEPENDENT_CODE ON` on the latter.
Keep project warnings scoped to project targets. Use the SDK's module entry and
bundle helpers, not an ad hoc shared-library layout.

The pinned source confirms `validator` is defined unconditionally on this Linux
path while `audiohost`/`editorhost` are behind the hosting-examples option; GTK/X11
are required by `editorhost`, which is excluded. Neither VSTGUI nor an audio
device/server is needed to run this command-line validator.

Proposed invocation after implementation; **not run by this worker**:

```sh
cmake -S . -B build-vst3 -DCMAKE_BUILD_TYPE=Release \
  -DRHODES_BUILD_VST3=ON \
  -DRHODES_VST3_SDK_ROOT=/absolute/path/to/vst3sdk \
  -DSMTG_ENABLE_VST3_PLUGIN_EXAMPLES=OFF \
  -DSMTG_ENABLE_VST3_HOSTING_EXAMPLES=OFF \
  -DSMTG_ENABLE_VSTGUI_SUPPORT=OFF \
  -DSMTG_ENABLE_WAYLAND_SUPPORT=OFF \
  -DSMTG_CREATE_PLUGIN_LINK=OFF \
  -DSMTG_RUN_VST_VALIDATOR=ON
cmake --build build-vst3 --target RhodesResearchVST3 validator --parallel 2
```

The SDK post-build step invokes `validator <bundle-path>`. Add an explicit CTest
without guessing generator-specific output directories:

```cmake
get_target_property(RHODES_VST3_BUNDLE RhodesResearchVST3 SMTG_PLUGIN_PACKAGE_PATH)
add_test(NAME vst3.validator.extended
    COMMAND $<TARGET_FILE:validator> -e "${RHODES_VST3_BUNDLE}")
```

Then run `ctest --test-dir build-vst3 -C Release -R '^vst3[.]validator[.]extended$'
--output-on-failure`. The actual validator accepts a bundle argument and `-e`
for extensive tests, returning nonzero on reported failures. Preserve the full
log and exit status. A passing validator establishes tested API conformity,
not DAW coverage, device deadlines, or measured instrument fidelity.
