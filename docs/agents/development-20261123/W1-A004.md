## Delivered behavior

The new standard-library CLI maintains a separate, fixed 100-assignment campaign
in five waves of 20. `init` refuses existing ledger/index files. `register A001
/root/w1_a001 "scope"` derives the wave and expected report path. Later waves
require every assignment in all previous waves to have a completed, intact report.
Actual task names must match the declared wave and assignment ID; registration
still relies on the integrator observing the actual collaboration launch.

`complete A001 [A002 ...]` hashes regular reports and refuses completion of an
already completed assignment. Validation detects altered reports, duplicate IDs,
malformed JSON, wrong wave/name/path mappings, and symlinks in campaign paths.
`validate --require-complete` requires all 100 completed assignments. `sync` repairs
the generated Markdown index; `sync --check` detects drift. Importing the module
does not run its CLI. Writes use staged replacement; a single integrator owns them.

The tool never reads or modifies the old setup campaign. No canonical new ledger
was initialized by this worker. The root integrator must initialize it and register
only actual task names returned by the collaboration service.

## Limits and handoff

This tool provides integrity and wave-order checks, not independent attestation
that an agent ran or that its findings were integrated. It assumes one writer;
it does not add multi-writer locking. Ledger and Markdown are separate atomic
writes, so interrupted generation is repaired with `sync`. The implementation
does not modify scientific task status or fidelity.
