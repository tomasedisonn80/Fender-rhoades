## Recommendation

Implement PHY-002 in a separate `contact_reference.hpp/.cpp` API with an explicit
physical timestep, state snapshot, controls, diagnostics and failure result. Keep
`ResearchEngine` and `ModalOscillator` as the existing synthetic impulse engine
and analytic baseline until a contact model has passed its own acceptance gates.
Do not replace a tested real-time primitive with an unbounded reference solve.

The current architecture makes that separation necessary:

| Existing boundary | Compatibility consequence |
|---|---|
| `ModalOscillator::configure` requires positive frequency and an underdamped mode | It cannot express the two-free-mass momentum fixture (`frequency=0`), or arbitrary critical/overdamping, without changing a deliberate public contract. |
| Modal rate is limited to 32–192 kHz | A stiff offline reference needs independent timestep refinement, potentially above 192 kHz. Raising the existing rate limit would not prove convergence. |
| `note_on` adds a velocity impulse immediately | A finite-mass launch has delay until collision and must retain a separate hammer state. Preserve the existing surrogate API and document a new launch API. |
| `set_sustain(bool)` switches damping exactly | Continuous damper travel requires a position/velocity input and contact geometry, not a floating-point reinterpretation of this switch. |
| Current process failure keeps partially advanced state | A reference retry must restore the complete last accepted state **and energy ledger**; it must not inherit this partial-advance behavior accidentally. |
| `mechanical_energy_joules` sums only modal kinetic and elastic energy | Contact reference totals additionally need hammer kinetic energy, all contact storage, optional damper/linkage storage, losses and external work. |
| Existing output observes state at `t`, then advances to `t+dt` | New snapshots and rendered output must retain an explicit timestamp convention; an unnoticed one-step shift invalidates impact-time and waveform comparisons. |

## Proposed implementation shape

1. **Pure constitutive evaluator.** Given compression and relative speed, return
   force, elastic storage, nonnegative loss power and a contact classification.
   Distinguish separated, compressed-force-bearing and compressed-clamped states.
   Do not evaluate fractional powers for negative compression. Validate all
   coefficients and define the supported exponent/range explicitly.
2. **Explicit model parameters.** Positive finite masses, nonnegative modal
   stiffness/loss, independent hammer/damper/pickup participation arrays, rest
   clearances and declared synthetic contact parameters. Zero modal stiffness is
   valid for the free-mass test. Keep mode count fixed or bounded, initially one
   mode and then two for coordinate-rescaling checks.
3. **Complete state.** Modal displacement/velocity, hammer position/velocity,
   physical time, and accumulated work/loss diagnostics. A launch or relaunch
   updates only the prescribed hammer/action state and records the full energy
   change. Resonator state is never reset. Reject/recover atomically.
4. **Separate continuous RHS and integration.** Implement the force and power
   balance independently of the selected stepper. This permits a different
   high-resolution method to test the implementation instead of comparing two
   invocations of the same routine. An offline RK reference can be useful, but
   does not remove the need for conservative-energy and nonsmooth-event checks.
5. **Accepted-step diagnostics.** Expose contact compression, force, branch,
   energies, interval and cumulative residual, accumulated absolute residual,
   impulse, event times/order, iteration/subdivision counts and failure reason.
   Preserve old values if a step is rejected. A passive bounded trajectory alone
   is not numerical accuracy evidence.
6. **Damper extension.** Add a declared oriented contact against prescribed
   linkage motion only after the hammer equations and ledgers pass. With
   compression `delta=b_d*q-y_d-g`, resonator force is `-b_d*F`, and linkage
   actuator power entering total modeled energy is `-F*dy_d/dt`. A different
   orientation is valid if all signs are transformed consistently. Record the
   port convention beside the API.
7. **Harness and build.** Add a dedicated reference executable/test target with
   current `rhodes_target_options`; keep output writing and fixture parsing out
   of the mechanics class. Reuse `PolynomialPickup` only as an observation of
   summed modal motion; it is not reciprocal magnetic mechanics.

## Numerical and modeling pitfalls

- Contact observation and generalized forces must share the exact same
  participation vector. Using the old `strike_coupling` values as independent
  impulses while observing a different compression breaks work reciprocity.
- For the stated clamp law, loss power is `c*delta^p*delta_dot^2` only on the
  unclipped branch. On a compressed zero-force branch, account for elastic
  storage decrease as `-k*delta^p*delta_dot`, not as the unclipped viscous power.
- Two supported modal masses do not conserve mechanical momentum in isolation;
  their springs exchange momentum with supports. Restrict the simple momentum
  test to zero-stiffness free masses or include support impulse.
- A relaunch that changes hammer position can also change contact storage. Its
  work cannot always be recorded as hammer kinetic-energy change alone. Prefer
  a separated launch location or account for the complete energy discontinuity.
- `q'_j=s_j*q_j` requires `b'_j=b_j/s_j`, `m'_j=m_j/s_j^2`, and matching stiffness
  and damping transformations. Keep natural frequency and decay invariant when
  those are derived from transformed mass/stiffness/loss. Include a negative
  scale in tests; positive-only scaling misses orientation defects.
- Endpoint sign-change detection misses grazing or two crossings within a
  timestep. Geometric separation and damping-clamp events are distinct roots.
- The old engine's frequency limit checks mechanical modes only. Nonlinear
  contact/pickup products can alias; no fidelity or alias-free claim follows
  from passing the original supported-rates test.
- Any ordinary adaptive or iterative reference solver must remain outside a
  host callback until capped-work, deadline and approximation-error evidence
  supports a runtime variant.

## Meaningful acceptance tests

Freeze constants, supported domain and observable-specific tolerances in the
integrator's commit **before** acceptance-test implementation, as required by
`docs/specs/CONTACT_REFERENCE.md`.

| Fixture | Discriminating assertion |
|---|---|
| Separated hammer and one mode | Exact zero force; oscillator compared at common physical times with independent closed form; hammer ballistic motion. |
| Conservative two-free-mass impact | Momentum conserved; kinetic plus contact potential energy bounded by the predeclared residual budget; positive impulse and physical rebound. |
| Supported resonator collision | Reciprocal work and consistent modal/contact energy, without an invalid free-body momentum assertion. |
| Damped impact crossing clamp | Both force-bearing and compressed-clamped branches exercised; no attraction; distinct correct dissipation ledgers. |
| Grazing, miss and short contact | Correct classification under signed clearance perturbations; onset/separation ordering and no missed collision on refinement. |
| Opposite-phase retrigger | Modal state unchanged at launch; distinct subsequent relative-impact velocity, impulse and rebound. |
| Two-mode scaling `(2,-3)` | Same reconstructed physical trajectory, contact force, energy and combined-motion pickup voltage. |
| Fixed damper / continuous pedal | Passive decay for a fixed boundary; signed actuator work balances moving-boundary energy; release preserves state. |
| `h,h/2,h/4,h/8` and separate solve/event tightening | Common-time trajectory, impact time, impulse, rebound and residual converge independently; no waveform time shifting. |
| Invalid inputs / exhausted step budget | Exact pre-step state and ledger restored; finite diagnostic failure; no accepted unconverged state. |

Keep the existing `core.retrigger`, `core.pedal_release`, `core.block_partition`,
`review.rejected_updates`, `review.engine_controls`, and
`review.engine_combined_pickup` tests unchanged as compatibility checks for the
existing engine. They encode its explicitly synthetic contract, so making them
exercise a physically different contact engine would silently alter that contract.
