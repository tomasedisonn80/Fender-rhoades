## Validation contract

The D entry point reads only `project/continuation-d-20261124.json` and its
completed canonical reports. It requires schema version 1, exactly 100 requested
agents in five waves of twenty, the existing concurrency-limit metadata of four,
and the exact `continuation-d-20261124` identifier. It retains strict JSON
parsing, including duplicate-key rejection, finite numbers, exact field sets
and integer checks that reject Boolean or floating-point substitutes.

Assignments must be consecutive integers in recorded order. Each assignment's
wave and `/root/w< wave >_< three-digit assignment >_< task suffix >` identity
must match its ordinal; task names must be distinct. Every earlier wave must
have all twenty completed records before any record in a later wave is accepted.
Within the current wave, workers may finish out of assignment order.

Running records contain only identity and status fields. Completed records add
the exact `docs/agents/reports/continuation-d/w< wave >-< three-digit assignment >.md`
path and lowercase SHA-256 digest. The actual report bytes must match that digest.
The helper checks path components for symlinks/reparse attributes, requires a
regular final file and checks that the resolved file remains within the supplied
repository root. Missing files, directories and FIFOs are rejected. Canonical
path checks prevent using another campaign's report even when its digest is valid.

The reported completion count is calculated from completed records with verified
reports and compared with `completed_agents`. A ledger declaring `complete`
requires all one hundred completed reports. Ordinary validation permits a
consistent in-progress campaign. `--require-complete` also requires the explicit
complete status, so an in-progress ledger with one hundred completed reports
still fails that final gate.

The configuration is supplied by the entry point, never selected by values in
the ledger. Unrelated campaign or canonical-state files are not parsed or changed.

## Focused test design and observed results

The new tests use temporary repositories and explicitly synthetic report text.
They neither depend on the moving live D ledger nor claim synthetic fixtures as
actual worker reports. Public CLI tests execute a new Python process from outside
the checkout and compare fixture path types, modification times and contents
before and after both successful and failing runs. Invalid input must return
exit code 1, write a D-labelled error to stderr, emit no success output and avoid
a traceback. Subprocess timeouts prevent a FIFO regression from hanging the suite.

The eleven test methods cover:

- Independence of C defaults and D configuration in the same Python process;
  valid partial D progress despite a separately malformed C ledger.
- A C ledger placed at the D filename, a C report with its matching hash,
  foreign report bytes under a D filename, and missing D metadata without fallback.
- Advancement past incomplete preceding waves, including early and late boundaries.
- False completed counts, premature complete status, explicit final completion
  and all one hundred genuine fixture report hashes.
- Reused names/reports, reordered assignments and noncanonical task identities.
- Strict numeric types, requested totals, status fields and record shapes.
- Duplicate status/count keys, nonfinite JSON numbers and invalid UTF-8.
- Changed registered report bytes, external/path-traversal substitutions with
  matching hashes and malformed digest spelling.
- Actual local symlinks for report files, parent directories and ledger files.
- A simulated Windows reparse attribute rejected before report bytes are read.
- Missing reports, directories and an actual local FIFO.

## Limits and next action

This validates recorded metadata and report bytes. It does not authenticate
actual agent execution, prove historical scheduling/concurrency, verify the
truth of report contents or establish scientific acceptance or physical fidelity.
Changing both report bytes and their recorded hash is outside what an unsigned
integrity ledger can authenticate. Baseline commits are checked for canonical
hexadecimal shape; the tool does not fetch or authenticate Git objects.

The existing helper checks the on-disk paths and bytes it reads. It does not lock
concurrent ledger/report writers or add atomic filesystem race protection. Use
the check on a coherent integration checkpoint; transient edits can require a
later read. The selected root is a trusted caller argument. This scoped refactor
does not broaden the existing C filesystem-security claims.

Next action: the integrator adds `python3 tools/validate_continuation_d.py` to the
Foundation integrity checks while the campaign is active, records this worker's
report at its next ledger checkpoint, and runs `--require-complete` only after
one hundred actual reports and explicit complete status are recorded. HOST-003
