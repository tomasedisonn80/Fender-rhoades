# Worker 008 — Expression controller audit

Date: 2026-11-24. Wave: 1. Scope: independent read-only review of the draft
Expression contract, controller APIs, and their fixtures. The only written path
is this report. No implementation, Git operation, canonical-state update, build,
CTest, SDK validator, or native-host experiment was performed.

## Finding

The proposed controller extension is compatible with the existing design, but
adding a parameter declaration alone is insufficient. The current controller
recognizes gain, sustain, and sixteen binary64 command controls; its decimal
helper conflates factor-unit syntax with the gain's maximum of 32. Expression
requires a third persistent-control path with maximum 1 and canonical binary32
values. Existing tests explicitly reject ID 2 and assume command enumeration
starts at index 2. Those assumptions must change without weakening command
precision or the exact legacy-unity state checks.

Sources: `plugins/vst3/controller.cpp`, especially `known_parameter`,
`parse_decimal`, `initialize`, both conversion methods, both state methods, and
`getMidiControllerAssignment`; `plugins/vst3/plugin_ids.hpp`; draft
`docs/specs/HOST_EXPRESSION_MONO_20261124.md`.

Freeze optional lowercase `x` acceptance for Expression explicitly in its text
fixtures: `0.5`, `0.5x`, `0.5 x`, and surrounding ASCII whitespace should mean the
same factor. Uppercase `X`, repeated suffixes, locale punctuation, embedded
whitespace inside the number, Unicode substitutes, and trailing junk remain
invalid. The existing decimal parser rounds to binary64 before domain checking;
therefore `1.000000000000000001` currently means exactly 1, whereas
`1.0000000000000002` must fail for Expression. Do not accidentally change that
established parsing convention.

Cross-owner dependency: `RhodesProcessor::collect_parameters` currently assigns
command duplicate-tracking slots with `2 + channel`. It must use `3 + channel`
when ID 2 becomes Expression; otherwise Expression and channel-zero CC123 share
the same seen slot. This is a processor integration requirement, not a controller
implementation performed by this worker.

## Floating-point edge handling

Reuse `include/rhodes/control_value.hpp` rather than native casts, comparisons
against zero, or host rounding changes. Its integer `quantize` implements
nearest-even binary32 conversion, and `widen` constructs exact binary64 bits
without DAZ flushing binary32 subnormals. Expression needs no divide/multiply
around these helpers. Both signed zeros become positive zero; negative
subnormals, values above 1, infinities, quiet NaNs, and signaling NaNs fail
validation before numerical arithmetic. Positive binary64 subnormals are valid
inputs but quantize to zero; positive binary32 subnormals remain nonzero when
widened and recalled.

The following literal normalized-input/output pairs are useful independent
fixtures for setting and text round trips. They were checked in this audit with
Python `struct` binary64/binary32 conversion under the available default host
environment; this does not test the C++ implementation or nondefault FP modes.

| Input binary64 bits | Expected canonical binary64 bits | Boundary |
|---|---|---|
| `8000000000000000` | `0000000000000000` | Signed zero |
| `3fb999999999999a` | `3fb99999a0000000` | Binary64 0.1 to binary32 |
| `3fe0000010000000` | `3fe0000000000000` | Even midpoint rounds down |
| `3fe0000030000000` | `3fe0000040000000` | Odd midpoint rounds up |
| `3690000000000000` | `0000000000000000` | Half least binary32 subnormal |
| `3690000000000001` | `36a0000000000000` | Immediately above that midpoint |
| `36a0000000000000` | `36a0000000000000` | Least binary32 subnormal |
| `36a8000000000000` | `36b0000000000000` | Subnormal midpoint |
| `380fffffe0000000` | `3810000000000000` | Carry into minimum normal binary32 |
| `3fefffffffffffff` | `3ff0000000000000` | Largest binary64 below 1 |
| `0000000000000001` | `0000000000000000` | Least positive binary64 subnormal |

Add maximum binary32 subnormal, minimum normal, largest binary32 below unity,
and exact unity cases. Keep command `0.1` equal to `3fb999999999999a` and least
positive command binary64 equal to `0000000000000001`; these prove the new
Expression branch has not reduced command precision. Reuse all supported
rounding modes, FTZ/DAZ combinations, and comma-decimal locales. Preserve caller
rounding/flush/exception-mask controls; the existing text fixture deliberately
does not promise unchanged sticky exception flags.
