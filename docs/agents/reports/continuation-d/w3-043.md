## Observed MSVC failure and fix

The supplied raw log was read from
`/tmp/rhodes-d-evidence/windows-3a2-build-failure.log`, SHA-256
`31a59b589a1c48ed63f7d83d5f6676e2701f685aa00bcaff5e3cd9cd6f2a90a9`.
It records Windows job `138457884481` building the earlier `3a2dbb7` source.
All three mono targets report C4805 at source lines 665, 671 and 991, accompanied
by C2220 because warnings are errors. The mixed operands are
`Steinberg::TBool` and `bool`.

The pinned SDK defines `TBool` as `uint8` in
`pluginterfaces/base/ftypes.h`; `Vst::Bus::isActive()` returns that type in
`public.sdk/source/vst/vstbus.h`. The current
[mono fixture](../../../../tests/cpp/vst3_mono_contract_test.cpp) converts the
result to a boolean predicate at every reported site:

```cpp
(host->processor.getAudioOutput(0)->isActive() != 0) == active
```

The first site uses `prior_activity` instead of `active`. Each comparison now
has two `bool` operands and still checks the bus's logical activation state.
This is a source-level diagnosis and review of the fix, not a claim that MSVC
has recompiled it. No additional C++ compiler warning/error family appeared in
the inspected failure log.

### ARM floating-point reporting

The controller's `fp_flush` selector returns 77 when MXCSR is unavailable, and
the three corresponding CTest registrations explicitly use
`SKIP_RETURN_CODE 77`. Its message says ARM flush modes are not exercised.
The AArch64 FPCR code observes control preservation during the supported
rounding cases; it does not install ARM flush/FZ16/FIZ modes.

The dependency-free `expression_state.floating_point_modes` selector has a
different reporting shape: it counts skipped combinations inside one test. On
the non-MXCSR branch, the three nonzero x86 flush combinations are skipped for
each supported rounding mode. With all four rounding modes available, this
means four executed combinations and twelve internal skips. Its enclosing
CTest can pass. A zero-skipped CTest summary therefore must not be reported as
ARM flush-mode coverage. Retain the selector's printed totals from its raw log
or JUnit output, as already identified in worker 039's review.

### macOS architecture and signing classification

Both new loader executables were added to the existing
`smtg_target_setup_universal_binary` / `smtg_target_codesign` loop. Inspection of
the pinned SDK helpers shows that the former sets `XCODE_ATTRIBUTE_*`
properties and the latter performs its configuration only under `XCODE`.
The current native workflow selects `Unix Makefiles` and deployment target
11.0, just as the existing native macOS route does.

Consequently the helper names are not evidence of a universal output or a
distributable signed product. Native results must be classified by the actual
runner/toolchain/architecture and built binary. This is an evidence boundary,
not a request to switch generators, change signing requirements or modify the
deployment target.

## Diagnostics and legacy comparison

Reviewed the actual workflow changes and the complete new
[diagnostic helper](../../../../tools/capture_ci_diagnostics.py),
[legacy comparator](../../../../tools/compare_vst3_legacy.py) and
[SDK-only recorder](../../../../tests/cpp/vst3_legacy_capture.cpp), along with
their focused Python fixtures and CMake registration.

The VST3 workflow checks out the fixed baseline revision separately, builds
the baseline modules with the same matrix arguments, creates the baseline
module manifest, configures the candidate with the baseline directory, and
requires matching detected compiler/generator settings. The candidate host
test aggregate includes the recorder and registers the legacy comparison only
when the required baseline manifest exists. The workflow supplies that path;
omitting it in a different local build remains missing legacy coverage.

The helpers use argument lists for native subprocesses rather than constructing
shell commands. CMake supplies the actual recorder target path, including the
Windows configuration/executable suffix. Comparator inputs are resolved before
use; bundle discovery recognizes `*-win/*.vst3`, `MacOS/<name>` and
`*-linux/*.so`. Audio is written in binary mode, and metadata explicitly names
native byte order, sample format, model IDs, latency, state checkpoints and the
allowed baseline/current parameter-count difference.

Every legacy capture retains its actual subprocess return code and must have
code zero before its JSON/audio can pass validation. Timeout or oversized
output also fails the capture. The comparator itself returns 0 only for a
complete successful matrix and 1 otherwise, so a native crash code is not
forwarded as a successful comparison. The diagnostic wrapper separately
retains child status and raw output, maps POSIX signal exits, refuses duplicate
labels and preserves command failures. Its Windows execution, including native
exception statuses and path handling, was not exercised in this review.

The raw diagnostic upload is under `always()`. Before/after metadata binds the
checked-out source, SDK revisions, compiler settings and modules, while a
missing or failed step is retained as incomplete evidence. No source inspection
can establish that an artifact upload actually occurred.

A read-only sizing check resolved one candidate integration concern: serializing
the helper's source/SDK snapshots into a minimal manifest-shaped object produced
708,340 bytes using the larger current tracked tree, below the comparator's
1 MiB manifest read bound. This used 1,044 current tracked files and 1,012 SDK
tracked entries; the frozen baseline tree had 950 tracked files. This is a
local sizing observation, not a native baseline-manifest execution.
