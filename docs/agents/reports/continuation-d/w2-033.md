## Reusable interface

The agreed CMake executable target is `rhodes_vst3_legacy_capture`. It uses C++20,
SDK headers and `rhodes_vst3_loader_support` exclusively; it neither includes
instrument/core headers nor links an instrument implementation. On macOS it
uses the existing loaded-host universal-binary/codesign setup. Platform module
loading remains the existing SDK loader's responsibility.

The integrator registered optional cache path
`RHODES_VST3_LEGACY_BUNDLE_ROOT`. A nonempty path registers
`vst3.legacy_unity_comparison`, with a 300-second CTest timeout, and requires a
baseline `manifest.json`. An unconfigured baseline does not manufacture a skipped
or passed compatibility result.

```sh
python3 tools/compare_vst3_legacy.py \
  --capture /tmp/rhodes-d-build/rhodes_vst3_legacy_capture \
  --baseline-root /tmp/rhodes-d-baseline-modules \
  --current-root /tmp/rhodes-d-build/VST3/Release \
  --output-dir /tmp/rhodes-d-build/legacy-comparison/Release \
  --sdk-root /workspace/scratch/d6370337c6a4/vst3sdk
```

`--capture`, `--baseline-root`, `--current-root` and `--output-dir` are required;
`--sdk-root`, `--source-root` and bounded `--timeout` are optional. No shell is
used to launch captures. Python uses only its standard library. Each baseline
manifest must contain `source_commit` equal to the fixed revision and three
`modules` entries with `path` and `sha256`. Paths may be absolute or relative
to the baseline root. Extra supplied build provenance is retained.

The roots directly contain the three bundles. Native binary discovery supports
Linux `Contents/*-linux/<variant>.so`, Windows
`Contents/*-win/<variant>.vst3`, and macOS `Contents/MacOS/<variant>`.
Discovery requires one native binary per variant and fingerprints every bundle
file. This portability design is not an observation that the implementation has
run on Windows or macOS.

## Frozen matrix and equality rules

The matrix contains 72 fixture descriptions: all three variants, binary32 and
binary64 host samples, 48,000 and 192,000 Hz, whole/fixed64/ragged callbacks,
and dense/sparse gain automation. Each fixture launches three separate OS
processes: saved baseline, current default Expression, and current explicit
Expression 1. Old and new modules have the same class IDs and are never loaded
into the same process. A full execution has 216 captures and 144 exact
baseline/current comparisons. Three captures can run concurrently, each with
its own process and output files.

The retained 2,048-frame note/gain/sustain timeline runs twice, with legacy
configuration recall and zero-frame flushes between epochs, followed by a
128-frame post-recall silence check. Every capture contains 4,224 stereo
frames. The adapted timeline includes 44 note events, 16 validated polyphonic
pressure events and 48 CC123 points, including deliveries on all sixteen
channels, shared holders, same-frame commands/notes, sustain and release tails.
The current explicit-unity lane supplies ID 2 at every callback and flush.

All six public class identities are literal independent expectations. The
baseline must expose 18 parameters and current modules 19, while the eighteen
legacy parameter descriptors must remain exact. The added Expression default
must be 1. Latencies remain 0/48/48 and the infinite-tail declaration is checked.
The intentionally corrected instrument factory subcategory is not an audio/state
comparison field.

The comparator uses no production state codec. Independently constructed
little-endian RHST v1 bytes specify the default state, every callback's final
gain/sustain state, both recalls, both flushes and the final reset. All snapshots
must be exactly 16 bytes. Metadata and audio compare exactly after excluding
only the declared lane differences: unique capture ID, lane name, total
parameter count and explicit Expression-point count. Stereo copies must also
match bit for bit, including signed zeros.

Dense gain provides an endpoint at every sample, so its whole/fixed/ragged
streams additionally form 36 exact partition groups across the three lanes.
Sparse callback endpoints depend on block size and are compared only between
matching partitions, following W1-017's warning about unequal delivered curves.
No tolerance is applied to legacy samples or state bytes.

## Nonvacuity, bounds and retained evidence

The recorder checks finite output, one sample canary after each declared channel
extent, actual silence masks, fixed output length, complete event/command counts,
and zero output after the final recall. Each musical epoch must have at least
128 nonzero left samples and a digital peak strictly greater than `1e-6`.
The Python comparator recomputes the nonzero counts, peaks, silence flags and
stereo identity from the raw bytes. Equal silence cannot pass. These digital
conditions provide nonvacuous compatibility evidence; they do not claim that a
device was listened to or perceptually validated.

Each invocation creates a fresh UUID-identified run directory. Each child also
receives a unique capture ID which must appear in its complete JSON record.
Existing child output files are refused. A stale passed `report.json` is replaced
by an incomplete current-run record before input validation. Missing fields,
unknown fields, duplicate JSON members, nonfinite numbers, wrong records,
partial samples, missing checkpoints, wrong legacy states and incomplete matrix
counts cannot pass.

The recorder writes at most 33,792 bytes per binary32 trace or 67,584 bytes per
binary64 trace. Parsed stdout is bounded to 128 KiB and stderr to 64 KiB. Child
wall time is limited (default 30 seconds, accepted range 1–60 seconds); output
files are monitored and excessive files are failed and reduced to bounded
diagnostic prefixes. A failed or incomplete child is recorded and never treated
as a comparison pass.

The output root's `report.json` names the fresh raw directory. That directory
retains each `.bin`, stdout `.json` and `.stderr`, plus `commands.json`,
`manifest.json` and a copy of the report. Per-case hashes, byte counts, all command
arguments, unique IDs, state-checkpoint hashes, callback counts, nonzero counts
and peaks remain in the report. The raw manifest is rechecked against the bytes
actually compared, including missing/changed/unexpected records. Before/after
fingerprints cover both sets of bundles, the recorder, baseline manifest and
relevant implementation/source inputs. Reports also retain OS/architecture,
Python, observed source HEAD, nearby CMake settings/cache hash and optional SDK
revision/submodule identity.
