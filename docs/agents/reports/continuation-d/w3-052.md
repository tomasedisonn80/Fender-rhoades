## Mailbox and transaction review

One `atomic<uint64_t>` stores gain bits 0–31, sustain bit 32, pending bit 33 and Expression bits 34–63.
Canonical valid Expression is at most `0x3f800000 < 2^30`; widening before the shift retains bit 63 without overlap. Literal mailbox words include the bit-63 transition, subnormal/normal edges, unity and signed zero.
`request_recall` always sets pending, including an identical newer request; snapshots acquire one whole word. `begin_block` consumes with one strong CAS; a conflict returns a nonpublishing token and defers recall without a retry loop.
`end_block` compares the entire cleared token, so newer pending writes win. `abort_block` restores pending only while the selected token remains current; it cannot replace a newer request. The contract has one serialized audio consumer and does not cover multiple consumers/replayed tokens.
Processor syntax copying completes before selection; ownership preflight uses a candidate. Ownership failure aborts before mechanics mutate. The selected recall installs before interpolation, whose offset -1 anchor is `live_state_`, never a potentially newer mailbox snapshot.
Zero-frame acceptance applies recall, final controls and releases without advancing audio time; rejected syntax/ownership preserves pending recall. The transaction fixture covers repeated abort/retry and a newer replacement between retries.
All mailbox operations are bounded and allocation-free in the reviewed source. No stream pointer is retained or accessed by `process`; UI stream helpers use fixed local storage.
The actual portability requirement is `atomic<uint64_t>::is_always_lock_free`, enforced at compile time alongside 8-bit bytes and IEC559 binary32. Pointer width alone does not establish lock freedom; no pointer-atomic requirement is substituted for this assertion.
