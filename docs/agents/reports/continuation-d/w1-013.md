## Golden boundary cases

1. Accept all 19 unique queues in several orders, including Expression directly
   beside CC123 channels 0 and 15. Reject duplicate persistent/command queues
   before reading their second queue's points; reject declared queue counts
   `-1`, `20`, and `INT32_MAX` without calling `getParameterData`.
2. Accept three 8,192-point controls plus sixteen command queues totalling 256;
   assert exactly 24,832 point reads. Reject each control's declared `-1`, 8,193,
   or `INT32_MAX` count before its first point read. Repeated equal offsets do
   not reduce the raw limit, including 8,192 offset-zero points during a flush.
3. Make Expression the last queue and its point 8,191 malformed/failed after
   the other 16,640 valid point reads. Require complete rejection, bounded output
   cleanup, unchanged mechanics/ownership/live/published state and pending recall.
   Exercise zero Expression too; muting must not bypass validation.
4. Preserve the existing 256/257 aggregate-command boundaries, including 256
   points followed by one in another queue: the overflowing queue gets zero
   point reads. Preserve the 585-action accepted construction in
   `vst3_command_bounds_test.cpp:135–183`.
5. Retain the existing per-offset boundary: 73 releases + 183 strikes accepts;
   adding sustain rejects 257; 73 + 182 + sustain accepts 256. Add simultaneous
   gain and Expression to these cases without changing their outcomes.

## Storage and callback observations

The new member array adds 8,192 `ParameterPoint` elements, ordinarily 65,536 bytes
on the supported 32-bit-field layouts, plus its count. Confirm actual `sizeof`
on each target before reporting an exact object size. Instance ownership avoids
adding this array to callback stack frames; do not create local full-array copies.
The existing local `NoteTracker` candidate/release temporaries remain a separate
stack question, not a proven platform maximum.

`ProcessorHost` already heap-owns `RhodesProcessor`; `ProcessorSnapshot` heap-owns
engine copies (`vst3_test_support.hpp:243–266,325–365`). Automation and partition
combined fixtures, buffer hosts, and the callback benchmark also use heap owners.
Preserve those patterns. Move the standalone processor in
`vst3_filtered_test.cpp:207` to a heap owner when extending that fixture.

Host `ParameterQueue::Point` carries a double: ordinarily 16 bytes, so a full
queue carries 128 KiB of point storage. Nineteen such queues carry 2.375 MiB,
already exceeding the cited 1 MiB Windows test-stack budget before other locals.
Allocate combined fixtures before callbacks, preferably three full persistent
queues plus sixteen 256-point `CommandQueue`s, all under one heap owner. The
current 18-full-queue allocation fixture is already heap-owned; retain that
ownership if simply extending it.

Update the two-slot `ParameterChanges`, 18-slot `CommandChanges`, and local
18-slot allocation wrapper deliberately; existing explicitly typed two-element
array assignments also need review. Extend `vst3_host_test.cpp:1040–1268`'s
calibrated eight-form C++ allocation guard to Expression success, late rejection,
recall, flush and 19-queue traffic across variants/formats/layouts. Its setup and
snapshot allocations must remain outside the guarded `process()` interval.
The guard does not measure arbitrary `malloc`, locks, foreign-host behavior,
stack maxima or deadlines. The benchmark explicitly does not measure allocation.
