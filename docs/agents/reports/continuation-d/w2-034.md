## Implemented behavior

### Source-bound diagnostics

The new standard-library-only helper provides `metadata`, `run`, `ctest`,
`baseline-manifest`, and `verify-toolchains` subcommands. Every Foundation job
and the VST3 job takes a before snapshot and an `always()` after snapshot.
Snapshots retain the actual source HEAD/tree, expected triggering SHA, tracked
status, index objects/modes, observed tracked-file SHA-256 values and a digest
of that complete manifest. A wrong HEAD, dirty tracked source, or a changed
before/after manifest fails the metadata gate. Missing before metadata remains
an explicit incomplete observation.

VST3 snapshots also retain and verify the unchanged official SDK root pin and
all four required submodule pins, together with their tracked-file manifests.
The legacy checkout is independently checked against the exact fixed commit.
Compiler paths, IDs, versions, generator/platform/toolset, relevant build
settings and hashes of CMake detection/cache files are captured when available.
OS, machine architecture, Python, Git, CMake and CTest versions accompany an
explicit allowlist of workflow/source/ref/event/run/attempt/job/runner fields.
The tool does not dump the complete environment or GitHub context.

`run` streams the complete combined stdout/stderr to the console and a binary
log, retaining the exact argv, working directory, start/end times, child exit
code, shell-compatible wrapper exit code, byte count and log SHA-256. It
returns the child's ordinary nonzero exit code, and records a signal's raw
negative code while returning its shell convention. A missing executable is
retained as an explicit start failure. Duplicate labels cannot replace an
earlier command's evidence.

`ctest` records the selected inventory with the same configuration/filter as
execution, then adds absolute raw-output and JUnit destinations. It executes
the selected tests once and preserves CTest's exit status. Each job retains:

- `ci-evidence/ctest-inventory.json` and inventory command/stderr records;
- `ci-evidence/ctest.log`, the complete combined terminal stream;
- `ci-evidence/ctest-output.log` and `ci-evidence/ctest-junit.xml`;
- `ci-evidence/ctest.command.json` with the actual command and exit status;
- the matching build's `Testing/Temporary/` directory, including original
  per-test output and failure lists when created.

All existing Foundation Python checks are individually wrapped; the full
verbose unittest run is retained in `ci-evidence/python-tests.log` and its
command record. Existing test selection and failure propagation are preserved.
A prior failed step can still prevent later tests from running; an absent
result is incomplete work, not a pass.

### Retention and native legacy gate

Every job has a final pinned `actions/upload-artifact` step with `if: always()`,
`if-no-files-found: error`, and requested `retention-days: 90`. Names include
the platform, architecture, source SHA, run ID and attempt. Foundation names
also include the job name. The existing manual-dispatch/retry isolation and
automatic-push supersession expressions were preserved exactly.

The native workflow now checks out the **same repository** at
`6c91dab00855b67a559e92edb79ae49e567be469` into `legacy-source`, with
`persist-credentials: false`. It configures `legacy-build` using
`BUILD_TESTING=OFF`, the same pinned SDK, Release configuration and matrix
generator/architecture arguments as the candidate. Only the three requested
module targets are built: `rhodes_vst3`, `rhodes_vst3_filtered`, and
`rhodes_vst3_quadrature`, plus their necessary build dependencies.

`baseline-manifest` writes `legacy-build/VST3/Release/manifest.json` only after
the fixed source, SDK and all three nonempty native modules are validated. Its
required fields are the fixed `source_commit` and three `modules` entries with
paths relative to the bundle root and observed SHA-256 values. The manifest
also retains the source, SDK, compiler/build and environment provenance, and
is copied into the diagnostic directory. A rejected attempt is retained there
with its reasons, without publishing a valid comparator manifest.

The candidate configure passes an absolute
`RHODES_VST3_LEGACY_BUNDLE_ROOT` pointing to that bundle root. Before building
the candidate, `verify-toolchains` compares the detected baseline/candidate
compiler identity/version/path, generator and relevant architecture/Release
settings, failing on a missing required identity or mismatch. The existing
`^vst3\.` CTest filter includes the integrator's new
`vst3.legacy_unity_comparison` registration. The entire
`build/vst3/legacy-comparison/` tree is uploaded with diagnostics, including
worker 033's report and unique raw capture subtree. The agreed full matrix is
216 bounded child captures and 144 exact comparisons; no reduced CI mode was
introduced by these workflow changes.

The native job timeout is 45 minutes to allow the additional baseline build
and full capture matrix. Changes to either diagnostic/comparison tool now
trigger the VST3 workflow. Existing action and SDK pins are unchanged.

Complete experimental bundle packaging remains success-only, after the final
source check. Its existing three-bundle resource/content/mode/symlink tar
verification and seven-day retention remain intact. Bundle artifact names now
include run ID and attempt, avoiding retry name conflicts. Diagnostics are
uploaded separately even when a test, metadata check, or packaging step fails.
