## Findings before capture

**Bind the reported SDK to the configured build.** `main` hashes the checkout
provided through `--sdk`, but never checks that its resolved path equals
`RHODES_VST3_SDK_ROOT` in the retained CMake cache. A different valid checkout
could therefore supply the purported SDK identity. Compare the two paths and
validate the actual configured checkout/pins before measurement. The inspected
cache currently points to `/workspace/scratch/d6370337c6a4/vst3sdk`.

**Stable hashes do not prove a fresh build.** The before/after input and executable
hashes detect changes during capture, but an already stale executable can remain
unchanged throughout. A source edit before launcher startup would be recorded as
the measured source even if it was never compiled. Retain a successful build
record and a no-work dry-run for the exact three benchmark targets before taking
the initial hashes. A dry-run is an additional freshness check, not a
cryptographic source-to-binary attestation. The review's actual
`ninja -C build/vst3 -n rhodes_vst3_benchmark rhodes_vst3_filtered_benchmark rhodes_vst3_quadrature_benchmark`
reported **no work to do**.

**Check the build contract, not only workload integrity.** A bounded negative
probe reused the test fixture and supplied `build.configuration="Debug"`,
`fast_math_macro=true`, a wrong machine label and an unknown timing clock.
`verify_result` still returned `valid=true`; these fields are retained but not
checked. Require the declared Release/no-sanitizer configuration before capture,
use the configured compiler's version command, and reject contradictory raw
configuration/machine/clock fields. The inspected current cache uses Release,
`/usr/bin/c++`, `-O3 -DNDEBUG`, and disabled project/SDK address sanitizers; this
review found no actual current-build mismatch. Fast-math and LTO should be
recorded explicitly rather than silently inferred from Release.

**Capture actual dependency inputs.** `source_paths` uses tracked suffixes and
a fixed initial path set. Generated or untracked included files, `.inc` files,
and `CMakeFiles/rules.ninja` are not generally covered by that selection. Add
the actual target dependency inventory, preserve complete compile/link commands,
and compare the inventory as well as its hashes. The official
[Ninja manual](https://ninja-build.org/manual.html), reviewed 24 November 2026,
documents `-t inputs` and `-t commands` for these purposes. A failed mandatory
metadata command should make the required evidence incomplete rather than leave
an otherwise successful manifest labeled complete. Retain configured compiler
identity rather than relying on whichever `c++` is first on `PATH`.

## Correct boundaries already present

Raw stdout/stderr have SHA-256 records; the exact plan bytes and canonical hash
are retained. Source and binary hashes are rechecked before every child and
after capture. CMake cache, compile commands, Ninja build definitions, SDK
revisions/status, linkage, cgroup limits, CPU topology, power/frequency availability,
affinity and competing-activity declarations are captured. Missing machine fields
are explicit. A final evidence-file hash inventory would additionally bind
execution/affinity/metadata files for portable verification.

All 36 same-profile/variant repeat pairs compare the eight frozen integrity
fields. Different variants are correctly not required to share an audio hash.
Duration summaries retain microseconds, nearest-rank percentiles, strict nominal
period misses, sorted binary64 means and a separate `fsum` result. Slow callbacks
do not become integrity failures; the limitation text distinguishes observed
period misses from audio-device underruns and worst-case bounds.
