# Wave 1 / assignment 17 — official VST3 contract review

Reviewed the current `plugin_ids.hpp`, processor/controller, state streams,
instrument-state encoding and `docs/VST3.md`. Source was read-only; only this
report changed. No build, test, canonical-state or Git mutation was performed.

## Findings

All six processor/controller FUIDs are distinct. `factory.cpp` publishes the
selected pair, and the processor constructor associates its matching controller.
The direct, filtered and quadrature variants select model IDs 1, 2 and 3,
respectively. Their **wire-format version is uniformly 1**: these are separate
model identities, not three format versions. `decode_instrument_state` checks
the selected model before recall, so a different variant cannot silently
reinterpret the 16-byte chunk. Controller recall validates the whole chunk
before changing parameters and makes no host component-handler callback.

`RhodesProcessor::getLatencySamples` returns 0, 48 and 48 for the respective
variants. Compile-time assertions bind the two delayed variants to their engine
latency. The official interface defines this value in samples and requires a
`kLatencyChanged` restart notification when latency changes [1]. Because the
variant is immutable and there is no live quality switch, the current lack of a
latency-change notification is appropriate; changing sample rate changes the
delay in seconds, not the reported frame count.

The SDK requires setup while inactive and processing transitions around actual
callbacks; `setProcessing` may execute on an audio thread and must stay light
[1,3]. Current setup prepares the engine before publishing configuration;
processing/activation transitions reset mechanics, note ownership and histories
while retaining configuration. This matches the documented boundary, assuming
the host synchronizes lifecycle calls. The source does not claim to tolerate
concurrent reconfiguration.

One focused future host check is worthwhile: the controller's `getState/setState`
currently persists gain/sustain as well as receiving processor state through
`setComponentState`. Steinberg distinguishes processor state from GUI-specific
controller state [2]. Exercise project restore with deliberately differing
processor/controller chunks to establish the intended precedence before adding
product UI. This is a compatibility question, not a reproduced failure.

No new definite API defect was established. Native DAW project restore,
sample-rate reconfiguration, latency compensation and cross-platform coexistence
still require actual host observation; SDK checks alone do not establish these.
