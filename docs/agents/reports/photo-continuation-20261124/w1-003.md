## Findings

### 1. White-key feedback paints over photographed black keys — concrete defect

`photo_geometry.hpp` deliberately gives white keys full six-vertex surfaces
underlying black trapezoids. Black-first hit testing resolves this correctly.
However, `PhotoView::draw_key` (`photo_editor.cpp:481`) fills and strokes that
entire polygon directly over the photo, without subtracting black surfaces.
Consequently, hovering or holding a white key can tint and outline part of a
neighboring black key. Hit correctness does not imply highlight correctness.

An in-memory Python calculation reconstructed the polygons from the committed
front-anchor arrays and checked each black polygon's vertex-mean point against
white polygons. All **30 of 30** black centers lie inside a white paint polygon;
examples are black MIDI 30 under white 29, black 32 under white 31, and black 34
under white 35. This corroborates the overlap already asserted by the C++ test.
The calculation establishes geometric overlap, not a newly captured screenshot.

**Recommended fix:** retain the current hit regions and immutable original
bitmap; define a separate visible white-key highlight path that subtracts the
overlapping black polygons, or clip the white fill/stroke to that visible
surface. Verify both a hover and a held white key adjacent to a black key.
Pixels inside the black surface should remain unchanged when only white-key
feedback is drawn. Include end-register and central-register examples.

### 2. Minimum-size feedback and switch targets are very small — usability risk

All painting and hit regions share the original-pixel transform, which is
correct. At the supported minimum 768 × 576, source scale is 0.5:

| Element | Logical dimensions / font size |
|---|---|
| Knob target | 25 × 25 px |
| Treble / Bass targets | 51.5 × 10 / 51.5 × 10.5 px |
| Vibrato target | 12.5 × 15 px |
| Pedal target | 23.5 × 45 px |
| Feedback primary / help text | 10.5 / 8 px |

At default 1024 × 768, help text is approximately 10.67 logical px. These
figures derive from source sizes; no accessibility threshold is claimed.
The panel/control rectangles align with the depicted controls on visual
inspection, including the pedal. Enlarging all targets uniformly would create
ambiguity among the close sliders, switch, and knobs.

**Recommended improvement:** preserve the photo and source hit transform, but
render the transient help/readout with a minimum logical font size, measuring
and clamping its bounds after layout. If pointer-target expansion is needed,
limit it by neighboring-control midlines and retain deterministic priorities;
test the resulting dead zones and overlaps at minimum size. Existing wheel,
Tab/Shift-Tab, arrow, Home/End and switch Space/Enter controls provide alternate
editing without changing the picture.

### 3. Transient feedback can become undiscoverable until a target change

`update_hover` returns early when the region ID is unchanged; feedback expires
after 1700 ms. Once it expires, moving within the same control does not restore
its readout. Keyboard focus is retained after that timeout, while native focus
drawing is disabled in `didOpen`. Pressing an editing key does bring feedback
back, but the focused parameter is invisible before that action.

**Recommended improvement:** refresh the existing transient feedback on
meaningful within-target pointer motion after expiry and on explicit keyboard
navigation. Keep the existing timeout, blur/Escape clearing, and exact photo
idle surface. Verify no idle overlay remains after the timeout.

### 4. Value feedback is coherent, but its contour is value-independent

`onIdle` reads the same controller values used by automation/state recall while
feedback is visible. The readout uses the parameter's plain value or switch
string. There is no parallel GUI state. The ring/rectangle in `draw_control`
only identifies the control; its position does not depict the current value.
The photographed knob, slider, switch and lamp remain unchanged, as required.

An optional transient normalized-position tick, slider guide, or On/Off accent
could reinforce the already-correct numeric readout while interacting. Any
such cue must disappear fully at idle and must not repaint or replace the
photographed controls. This is an enhancement, not a missing required feature.

### 5. Keyboard/pedal semantics need one small wording correction

The 73 keys map to MIDI 28–100, with 43 white and 30 black polygons. Audition
uses one mouse-held note per view, fixed velocity 0.75, and supports drag between
keys. Leaving the keyboard releases that view's note; click pedal toggles the
shared Sustain parameter. Existing mouse-up, cancel, blur, window-deactivate
and removal paths attempt release and close gestures. This audit did not
execute their native event delivery.

The tooltip says “release to stop” (`photo_editor.cpp:511`). Release tails and
an enabled Sustain pedal mean this can promise more than the model does.
Prefer “Click and drag to audition; release the key” and make the pedal's
latching On/Off behavior explicit in its transient help. Keep its parameter
mapping and original photograph unchanged.

## Positive checks and remaining limits

- Draw, pointer hit tests and host parameter finding use `AspectFit` and the
  same source space. The original full 1536 × 1152 composition, cabinet, legs,
  pedal and background are retained in the inspected idle screenshot.
- Exact 4:3 native constraints quantize width in units of four, bound logical
  width to 768–1536, and reject unconstrained sizes. Constraints currently use
  width as authoritative; vertical-only resize requests therefore do not choose
  a new width. Treat support for that gesture as an optional UX decision.
- Black keys have explicit precedence including shared boundaries; equal-color
  boundaries choose the lower index. Nonfinite coordinates and out-of-range
  indices reject. The existing test checks all 73 polygon centers, measured
  front anchors, black edges, transforms and invalid inputs. Tests were read,
  not executed by this worker.
- Feedback boxes are clamped horizontally and remain within the source bounds
  for the current keyboard and control anchors. Full-path white painting is
  the identified clipping issue; no crop of the idle photo was observed.
- This review makes no new attached-window, DAW, audio, native platform,
  screenshot-equality, or accessibility-conformance claim.
