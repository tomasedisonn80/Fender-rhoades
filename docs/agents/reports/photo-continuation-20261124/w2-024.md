## Integrated review findings

### 1. The setter is also a synchronous callback boundary

`RhodesController::setParamNormalized` advances the persistent parameter's revision before delegating to the SDK setter (`controller.cpp:406–421`). The SDK can synchronously notify parameter dependents. Existing controller revision tests deliberately exercise nested setter callbacks through `Observer::update` and `observer_cases` (`vst3_controller_revision_test.cpp:190–262`), including an equal-value nested write that advances the revision without another SDK value-change notification.

Consequently, guarding only `beginEdit`, `performEdit`, and `endEdit` is insufficient. A parameter observer may cancel the view during its provisional setter, causing `endEdit` before that setter returns. Calling `performEdit` afterward would be outside the accepted gesture.

The reviewed fix now checks cancellation immediately after the setter (`photo_editor.cpp:410–419`) and suppresses the perform call. It also checks for a nested write to the same parameter and suppresses publication of a superseded value.

**Required runtime follow-up:** install an actual SDK dependent in the production-view fixture, cancel from its one-shot change callback, and require the literal trace `begin(0), end(0)` with no perform, no captured motion, and the original controller value when no newer host write occurred. The existing view fixture's hooks cover the component handler and audition transport, but do not yet install a parameter dependent.

### 2. The submitted revision must be captured before the setter

Capturing `parameterRevision(tag)` after `setParamNormalized` returns cannot identify the provisional UI write: a synchronous observer may already have performed a newer setter call. An equality comparison of parameter values is also insufficient, because a newer host setter may intentionally write the same canonical value.

The reviewed code calculates `submitted_revision = parameterRevision(tag) + 1` before calling the setter (`photo_editor.cpp:401–404`). It rolls back a failed perform only when the current revision still equals that stamp (`photo_editor.cpp:422–424`). The controller's stamp increments before observers, including accepted equal-value setters (`controller.cpp:418–421`), providing the required distinction.

**Required runtime follow-up:** on a rejected `performEdit(0, 0.52)`, synchronously call `setParamNormalized(0, 0.52)` and require the final value to remain 0.52. Exercise with and without view cancellation. Also test a newer unequal value, and a write to another parameter: another parameter's revision must not prevent rollback of this rejected edit. Existing `perform_cancel_host_update` tests only the unequal 0.75 write after cancellation (`photo_view_interaction_test.cpp:581–594`).

### 3. Cancellation before perform requires conditional provisional rollback

The first reviewed patch returned immediately after detecting cancellation inside the setter. That prevented an invalid perform but left the locally installed value active even though the host had received no perform notification. Example: seed 0.5, attempt wheel value 0.52, cancel in the parameter observer; the host trace ends at `begin, end` while the controller would otherwise retain 0.52.

The final source now restores `previous` in this cancellation branch only if the parameter revision still equals `submitted_revision` (`photo_editor.cpp:413–417`). A nested host write retains authority because it changes the revision. This is distinct from cancellation during an accepted perform, which correctly preserves the accepted value.

**Required runtime follow-up:** test both cancellation-only rollback to 0.5 and cancellation plus a nested same-value or different-value host write that must survive. A rollback setter can itself notify dependents, so use a one-shot callback and verify no extra gesture or perform is emitted.

### 4. Guard release callbacks before starting the next audition note

A glissando first releases its current key. That release can call host allocation and receiver notification code, and either callback may cancel the view. A generation check scoped only around the subsequent down would start too late and allow a fresh note after cancellation.

`move_audition` now takes its snapshot before `release_key`, compares immediately afterward, and returns before a new down when cancellation occurred. `onMouseDownEvent` likewise verifies that its own cancellation advanced the generation exactly once; nested cancellation from either an old gesture end or old-key release aborts the new press. Equivalent cancel-then-edit/Tab guards exist in `onKeyboardEvent`.

**Required runtime follow-up:** hold key 0, arrange cancellation during its up's receiver callback or message-allocation callback, then move toward key 1. Require only key 0 down/up, no key 1 down, and inert later captured movement. Add the same cancellation while a new control press or keyboard edit tries to end a prior gesture. Existing `audition_drag` and `audition_cancel_allocation` cover ordinary transfer and initial down cancellation, respectively, but not old-key release cancellation (`photo_view_interaction_test.cpp:596–648`).

## Pending controller transport issue: emergency before an in-flight down

This is a precise source-derived trace, not an executed reproduction in this worker.

1. Owner A requests down on key K. `auditionNote` stores `state->key = key` before calling `sendAuditionNote` (`controller.cpp:268–270`).
2. `sendAuditionNote` calls host `allocateMessage()` before filling or sending the down (`controller.cpp:277–288`). The fixture already demonstrates that this boundary can invoke synchronous user-supplied code (`Application::createInstance`, `photo_view_interaction_test.cpp:186–210`).
3. During that allocation callback, a legitimate controller emergency runs. For example, a nested sibling transport failure invokes `releaseAuditionNotes` through `auditionNote`'s failure path (`controller.cpp:271–274`). A focused regression can directly call public `releaseAuditionNotes` from the allocation hook.
4. `releaseAuditionNotes` clears every owner's key and sends `RhodesPhotoReleaseV1` (`controller.cpp:291–305`). If accepted, the pending-release flag becomes false before the outer down resumes.
5. The original allocation returns, its down is filled and sent, and the receiver can accept it after the release. The resulting wire sequence is `ReleaseAll, Down(K)`, with no owner for K.
6. The view's cancellation generation may be unchanged. It can publish `held_key_ = K`; later idle clears the visual state when `heldAuditionKey` reports -1. An owner-specific release is suppressed by `if (state->key != key) { return true; }` (`controller.cpp:258–261`), so it cannot repair the orphaned accepted down.

**Action:** add a controller/view regression that records actual wire order and final receiver-held state. A controller transport epoch or equivalent serialization must distinguish an emergency that happened while a down was being constructed, and must suppress that stale down before sending or reliably compensate if it was already delivered. Merely checking owner state after a successful send cannot release an orphaned key through the current owner-specific API. A notify-time emergency deserves its own ordering case because the receiver may already have accepted the down.

Retain owner-specific cleanup for ordinary focus cancellation. Routing routine cancellation through `releaseAuditionNotes` would disturb sibling owners and would not by itself solve the allocation ordering race.

Root acknowledged this as a separate pending issue and plans a dedicated controller regression assignment.
