# W1-002 — Closed-device parameter persistence review

Worker: actual worker 2/100, wave 1/5. Assigned baseline: `e2aa41c`.

## Finding

The observed stale-save mechanism is consistent with missing host parameter delivery, not a state-stream encoding failure. The plug-in already implements the VST3 zero-frame flush path. A change visible in the controller cannot reach the processor's saved configuration until the host delivers it through `process()` or explicitly restores processor state. The retained REAPER visual evidence does not establish whether the host omitted flushing or supplied a flush that the plug-in rejected. Instrument that distinction before changing production behavior.

## Source trace

- `plugins/vst3/photo_editor.cpp`, `change_value()`: stores the canonical controller value, calls host `performEdit()`, and rolls the local value back if the host rejects the edit. Gestures use `beginEdit()`/`endEdit()`.
- `plugins/vst3/controller.cpp`, `setParamNormalized()`: validates/canonicalizes and changes controller parameters only. `getState()` serializes all eight current persistent controls. `setComponentState()` installs the decoded controls locally; `setState()` calls that same function.
- `plugins/vst3/processor.cpp`, `getState()`: serializes `mailbox_.snapshot()`. That snapshot contains the last successful audio publication or a pending explicit recall; it cannot infer undelivered editor edits. `notify()` currently accepts audition note/release messages, not parameter changes.
- `plugins/vst3/processor.cpp`, `validate_buffers()` and `process()`: accept a zero-frame flush before processing setup, with no output bus, or a zero-channel/negotiated-width bus without sample pointers. Only offset-zero parameter points and an empty event list are accepted. After full input validation, the flush updates controls and publishes their coherent state without advancing the frame cursor.
- `include/rhodes/plugin_state.hpp`, `PluginStateMailbox`: audio publication is bounded and makes one ownership attempt. The revision token prevents an old block from overwriting a newer recall. Snapshots include pending recalls without consuming them.
- `plugins/vst3/state_stream.cpp` and `include/rhodes/plugin_state.hpp`: the writer exports adaptive 16/20/40-byte v1/v2/v3 packets according to canonical expression/panel values. Nothing here queries controller state; changing the codec cannot recover an absent parameter delivery.

## Host contract and restore ordering

The official [Steinberg communication FAQ](https://steinbergmedia.github.io/vst3_dev_portal/pages/FAQ/Communication.html) assigns delivery after `performEdit()` to the host. When its audio engine is stopped and the plug-in remains activated, the host must periodically send a bufferless parameter flush. It explicitly identifies stale saved state as a consequence of absent flushing. A closed audio device alone does not prove the plug-in remained activated.

The official [Steinberg persistence FAQ](https://steinbergmedia.github.io/vst3_dev_portal/pages/FAQ/Persistence.html) specifies saving component state followed by controller state, and restoring component `setState()`, controller `setComponentState()`, then controller `setState()`. With this implementation, a newer controller chunk can therefore restore newer knob positions after an older component chunk. That does not itself update the processor: a UI/DSP mismatch remains possible unless the host separately delivers the parameters. The controller chunk is not sufficient proof of correct musical recall.

The local SDK additionally documents `setParamNormalized()` as a GUI update that must not echo back through the component handler (`pluginterfaces/vst/ivsteditcontroller.h` in `/workspace/scratch/d6370337c6a4/vst3sdk`).

## Safe bounded resolution

Preserve the existing parameter queues and state codecs. At the host integration boundary, serialize access with audio processing, flush pending edits using `numSamples = 0` and no audio buffers, then call component `getState()`. This uses the existing validated fixed-capacity parameter path and preserves sample-offset automation, defaults, model identities, and current lifecycle behavior. For a third-party host that never delivers the edits, record an exact host limitation; no production plug-in fix is justified by the available trace.

Do not substitute an unsolicited controller-to-processor parameter back channel or call `request_recall()` for GUI gestures. `install_recall()` deliberately resets mechanics, MIDI/UI ownership, audition queue prefix, cursor/history, and effect state. Such a substitution would alter the established gesture and automation semantics. Likewise, `getState()` must not touch audio-owned live state or call `process()` itself while the host may own processing.

## Required regression and named-host evidence

1. Load the real module through its factory, connect processor/controller, and install a recording host component handler. Repeat for all three variants. Record lifecycle calls, accepted begin/perform/end edits, and every `process()` call's frame count, queue IDs/offsets/values, and return code. Capture into bounded diagnostic storage; write logs off the audio thread.
2. Change persistent controls through the editor gesture path while deliberately withholding all process calls. Save both chunks. Assert that controller state contains the edits and component state still contains the previous configuration. Restore both into a fresh instance in the official order and check component and controller independently. This is the negative control demonstrating missing delivery, not a plug-in pass criterion.
3. In the matched positive case, deliver the recorded edits in an accepted zero-frame flush before saving. Require exact component/controller control agreement and fresh-instance recall. Check unchanged cursor/mechanics without an explicit recall, canonical booleans, v1/v2/v3 adaptive lengths, and model identity. Cover rejected flushes preserving pending recall/configuration, plus normal audio automation after resumption.
4. Run the same edit/save/reopen sequence in actual REAPER with device closed, recording whether the plug-in is active and whether flushing occurred. Compare the saved component payload and recalled audio-state controls, not only host parameter listings or screenshots. Repeat with an operating audio engine as the positive host comparison. A rejected actual flush requires its concrete input shape to reproduce before relaxing validation.
