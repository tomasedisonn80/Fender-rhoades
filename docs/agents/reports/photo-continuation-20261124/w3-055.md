# Worker 055 — Native X11 child ownership

Read-only source review; no build/native execution or production/SDK edits.

In pinned `vstgui4/vstgui/lib/platform/linux/x11utils.cpp:35–60`, `ChildWindow`
allocates its own XID and creates a child beneath the borrowed host parent;
`:88` has an empty destructor. `x11frame.cpp:320–339,660–663` unregisters
the window handler, destroys members in reverse order (timer/drawing resources
before the child), then exits the run loop. The connection therefore remains
available during child destruction. With another frame alive, disconnect cannot
provide this cleanup.

Recommend one generated `x11utils.cpp` overlay, adding `<cstdlib>` and replacing
the unique destructor anchor:

```cpp
ChildWindow::~ChildWindow () noexcept
{
    if (auto connection = RunLoop::instance ().getXcbConnection ())
    {
        auto cookie = xcb_destroy_window_checked (connection, id);
        std::free (xcb_request_check (connection, cookie));
    }
}
```

[XCB's checked request](https://xcb.freedesktop.org/manual/group__XCB____API.html)
keeps its error outside the event queue. A parent already destroyed, or a
server-rejected creation, can produce an expected `BadWindow`; freeing the
returned error keeps this destructor nonthrowing.
[Request checking](https://xcb.freedesktop.org/manual/group__XCB__Core__API.html)
syncs as needed: no extra flush or event pumping is required, at the cost of
a blocking teardown roundtrip. An asynchronous alternative requires explicit
`xcb_flush` and leaves errors to the shared loop.

`VstguiX11Lifetime.cmake:89–97,126` correctly finishes Cairo only at final
run-loop use, before disconnect; retain that boundary for sibling survival.
Never finish/disconnect from the child destructor.

Completed-child unwinding is covered; exceptions inside its own constructor
bypass its destructor, and failed `Frame` construction can leave the existing
run-loop count incremented. This patch does not establish general construction
failure recovery or native-platform acceptance.
