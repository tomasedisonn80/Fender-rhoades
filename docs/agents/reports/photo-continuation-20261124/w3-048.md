# W3-048 — X11/Cairo same-view reopen

## Scope and finding

Read-only review of the current photo editor and pinned VSTGUI
`5db272256172557818b6158cf0bb2c4410bddb25`. No build, runtime experiment, or test
was executed. The reported assertion is consistent with unfinished Cairo device
state surviving XCB connection teardown; the exact retaining object remains an
inference.

## Source evidence

- `plugins/vst3/photo_editor.cpp::close_now()` delegates structural teardown to
  `VST3Editor::close()`. The SDK retains `description` until editor destruction
  (`vst3editor.cpp`, constructor/destructor), allowing the decoded photograph to
  survive same-view reattachment.
- SDK `linux/x11frame.cpp::DrawHandler` creates an XCB surface/device. Its
  destructor removes the factory entry; `CairoGraphicsDevice` only calls
  `cairo_device_destroy()`. `Frame::~Frame()` destroys its implementation before
  calling `RunLoop::exit()`.
- SDK `linux/x11platform.cpp::Impl::exit()` disconnects XCB only when the last
  frame releases `useCount`. It never calls `cairo_device_finish()`.
  `x11platform.h` already declares an otherwise undefined `setDevice()`.
- The corresponding Wayland run loop retains its device and explicitly finishes
  it before connection teardown. Cairo's [device API contract](https://www.cairographics.org/manual/cairo-cairo-device-t.html#cairo-device-finish)
  distinguishes decrementing a reference from releasing external resources.

**Plausible mechanism:** a retained bitmap snapshot or font cache keeps the old
Cairo device alive; allocator reuse of the disconnected XCB pointer associates
the new connection with stale setup/screen state. This explains intermittent
success without a production change, but requires runtime confirmation.

## Bounded fix and verification

Use a hash-checked SDK overlay: retain the XCB surface's device in the run loop
through an idempotent `setDevice()`; finish and release it only on final
`useCount == 0`, before `xcb_disconnect()`. Clear the retiring device pointer
before cleanup and clear `xcbConnection` immediately after disconnect. Handle
null/error surfaces. Finishing each frame's device would invalidate another
live frame sharing the connection. Existing released XKB pointers and cursor
IDs also merit reset during final cleanup.

Keep the full reopen gate. First require an observed photograph paint: current
`attach()` proves geometry only, while the redraw timer runs at 16 ms. Repeat
paint → accepting-begin removal → actual deferred timer → empty registrations
and absent child → same-view attach/paint/input. Also close one of two open
editors and verify the survivor still paints and accepts input.
