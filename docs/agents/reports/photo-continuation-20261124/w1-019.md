# Wave 1 worker 019 — reentrant whole-editor close deferral audit

Date: 2026-11-24. Assignment: bounded read-only design review of `PhotoEditor::close`, actual SDK event deferral, editor lifetime, and regression entrypoints. No implementation or SDK edits, builds, tests, Git operations, state changes, or subworkers were performed. The only added file is this report.

## Finding and recommendation

The current synchronous `PhotoEditor::close()` can remove the child list while the SDK is still traversing it. A public SDK API exists to defer work until a frame event returns, but a one-stage `doAfterEventProcessing([self] { self->VST3Editor::close(); })` is **not sufficient evidence of safe native teardown**. This SDK drains that queue before its Linux native mouse handler returns. That handler still accesses its own window/implementation after the frame callback.

Recommend a narrowly scoped wave-2 implementation and regression study: cancel interaction immediately; retain the editor; gate structural teardown on the outermost frame event boundary; then perform teardown on a later UI run-loop turn using a checked timer. The two-stage timer proposal requires actual native reproduction and successful native regression before shipping. This report establishes source findings, not a passing implementation or a cross-platform safety claim.

## Source evidence

Paths below are relative to the inspected repository or to `/home/agent/rhoades-9a04c9726e31/vst3sdk` as identified.

1. **Existing close path.** Repository `plugins/vst3/photo_editor.cpp`, `PhotoEditor` around lines 615–693: destructor calls `close()`; `close()` calls `VST3Editor::close()` synchronously; `willClose()` cancels the view then clears `view_`. `open()` refuses an existing frame. These methods have no pending-close state or retained asynchronous owner.
2. **Invalidated child references.** SDK `vstgui4/vstgui/lib/cviewcontainer.cpp`, `dispatchEventToSubViews` around 988–1008 and `onMouseDownEvent` around 1024–1089: both bind `const auto& pV = *it` to a child-list element, call the view, and then inspect that element again. Retaining the `PhotoView` object alone does not preserve the erased list node. Wheel uses `dispatchEventToSubViews`.
3. **Actual public API.** SDK `vstgui4/vstgui/lib/cframe.h`, lines 189–205: both overloads of `doAfterEventProcessing` return whether work was queued; use is allowed only while `inEventProcessing()` is true. Implementations at `cframe.cpp` 1886–1904 merely push when `inEventHandling` is true; they do not schedule general asynchronous work.
4. **Nested guard behavior.** `CFrame::Impl::PostEventHandler`, `cframe.cpp` 96–119, saves the old handling flag, sets it true, then restores the saved value and drains a swapped local queue. It drains at each nested guard exit, not only the outermost exit. Therefore a deferred callback must inspect `inEventProcessing()` again and requeue if it is still true. The local swap means this requeue waits for a subsequent enclosing boundary instead of looping inside the same drain.
5. **Frame dispatch boundary.** `CFrame::dispatchEvent`, `cframe.cpp` 757 onward, constructs `PostEventHandler` first and `CollectInvalidRects` second. The latter owns a `SharedPointer<CFrame>` and is destroyed before the deferred callbacks drain. `platformOnEvent` at 1704 simply calls `dispatchEvent`. Drag and touch entrypoints have their own guards; activation callbacks inspected nearby do not all have that guard. Do not infer that `inEventProcessing() == false` proves no native callback is active.
6. **Editor retention precedent and frame-refcount trap.** SDK `vstgui4/vstgui/plugin-bindings/vst3editor.cpp`, `requestRecreateView` around 1075, captures `Steinberg::IPtr<VST3Editor>(this)` before deferral. `IPtr` adds/releases the VST3 reference (`pluginterfaces/base/smartpointer.h` 126–155). However, `VST3Editor::close` around 1373–1428 removes all children, then only sets `frame = nullptr` in the frame-reference-count-equals-one branch; otherwise it calls `forget()` and leaves the pointer. Do not retain a `SharedPointer<CFrame>` across the base close merely to make a callback pointer look safe: it changes the teardown branch. Retain the editor; bind the raw frame identity to an attachment generation.
7. **Native Linux boundary is later.** SDK `vstgui4/vstgui/lib/platform/linux/x11frame.cpp` around 436–516 calls `frame->platformOnEvent`, then mouse-down calls `grabPointer()` and potentially accesses `window` for focus; mouse-up calls `ungrabPointer()`; move accesses `window` again. `Frame::Impl` is owned by `Frame` through `unique_ptr`, and `Frame::~Frame()` destroys it. In `x11frame.h`, `onFrameClosed()` is empty. `x11platform.cpp` around 194–220 dispatches through a raw `IFrameEventHandler*`; the inspected path supplies no handler lifetime guard. Closing the native frame at the frame queue boundary can consequently invalidate the native handler before its post-callback work. This is a source-level hazard, not a runtime reproduction performed here.
8. **Public lifecycle wrappers matter.** SDK `public.sdk/source/vst/vstguieditor.cpp` around 183 calls virtual `close()` and then `EditorView::removed()`. Its `attached()` implementation calls `EditorView::attached()` even if virtual `open()` returned false. Therefore pending-close rejection needs an explicit public `attached()` guard, and an editor lifetime guard around the complete public `removed()` call is stronger than retaining only inside `close()`.

## Concrete implementation outline for wave 2

Use an explicit UI-thread-only lifecycle state, for example `open`, `pending_close`, `closing`, `closed`, `destroying`, and an attachment/close generation. Keep at most one scheduled completion for a generation. These names describe a proposed implementation, not existing code.

### Request and immediate logical cancellation

- `removed()` retains `Steinberg::IPtr<PhotoEditor>{this}` around the complete base `VSTGUIEditor::removed()` call. This protects the code after virtual `close()` if a host callback releases its last external editor reference.
- Normal `close()` retains the editor before any cancellation that can call the host. If already pending/closing/destroying, return without duplicating scheduling or cleanup.
- Set `pending_close` and bind the current frame/generation **before** calling the view. Mark the view permanently unavailable for new interaction for this attachment, then cancel gestures and owned audition notes immediately. Keep the child installed until structural teardown. Clearing `view_` or removing children is not the cancellation mechanism.
- The view's reentrancy/epoch work must prevent an in-flight accepted `beginEdit` or note-on from restarting a gesture after this cancellation. Current `cancel_interaction()` alone is not proof of that property. Its logical cancellation and stale-callback handling are a prerequisite shared with the PhotoView interaction work.
- While pending, reject `attached()` explicitly before calling the SDK, reject `open()`, and suppress parameter hit testing/new UI actions. Repeated `removed()`/`close()` must not reset the generation, replace the pending owner, or queue another close.

### Scheduling and physical teardown

The continuation owns a `Steinberg::IPtr<PhotoEditor>` and the expected attachment generation/frame address. It must validate generation and lifecycle state before dereferencing a raw frame address.

```text
request_close:
    retain editor
    mark pending + current generation
    stop new view interaction; cancel current interaction
    arrange completion for this generation

frame_boundary_completion:
    if generation/state no longer match: return
    if current frame is processing an event:
        queue this completion with doAfterEventProcessing; verify true
        return
    arm one checked UI timer for a later run-loop turn

timer_completion:
    retain continuation ownership for the entire callback
    if generation/state no longer match: return
    if current frame is processing a reentered event:
        return to frame-boundary scheduling
        return
    transition pending -> closing before invoking any delegate/host callbacks
    perform synchronous qualified VST3Editor::close exactly once
    clear view identity and transition to closed
    retire timer and retained completion; do not access editor after final release
```

Use `CVSTGUITimer` with an explicit `start()` result and explicit ownership/cleanup; `VSTGUI::Call::later` is public but returns no scheduling success and hides failure handling. Timer scheduling should not silently become synchronous teardown when the frame/native stack is still active. Define failure behavior before implementation: preserve the cancellation and pending owner, report/record failure, and provide a later safe retry; do not trade a failed timer for the original use-after-free. This is also why timer-start failure must be tested rather than assumed impossible.

For known ordinary lifecycle calls outside native callbacks, a synchronous path may preserve existing behavior. It must be established explicitly; `!inEventProcessing()` alone is insufficient because the SDK's activation paths are not all guarded. A conservative candidate defers all live-frame teardown, but that changes the timing of native child destruction relative to host parent destruction and requires the native host fixture below. Do not silently claim that tradeoff is solved by a nominal delay.

### Destructor and reopen rules

- The destructor must never call the asynchronous request method or construct an owning `IPtr(this)`: the reference count may already be zero. A pending continuation's owning reference should make destructor entry impossible until that continuation releases it.
- The destructor takes a separate non-retaining synchronous cleanup path, sets `destroying` first, and clears the delegate after cleanup. Assert/document the invariant that no deferred close remains. Do not turn destructor entry during an active dispatch into object resurrection.
- A host that releases the last editor reference inside a callback **without first requesting removal** is a separate lifetime case. A close-only fix does not cover it. Either establish the caller ownership contract for that case or retain the editor at the event/lifecycle entry boundary before any host callback; retaining it only after destructor entry is invalid.
- Reopen succeeds only after the previous completion has finished and its token is retired. Increment the attachment generation on the next successful attachment. An old callback must not close the new frame even if allocation reuses the same pointer address. Keep `closing` set through delegate callbacks so reentrant open cannot replace `frame` during base cleanup.

## Regression fixture entrypoints and required assertions

Existing `tests/cpp/photo_view_interaction_test.cpp` includes the real production translation unit and provides real-controller `Handler::on_begin`, `on_perform`, `on_end`, `Application::on_allocate`, and `Receiver::on_note` hooks. It is the right place to reuse independent edit/wire oracles, but its current fixture deliberately calls `PhotoView` handlers directly, retains a detached view, and does not cover whole-editor close. `tests/cpp/vst3_photo_editor_test.cpp` is also explicitly unattached and cannot close this gap.

Add a native editor fixture using the production `PhotoEditor`, public `IPlugView::attached/removed`, a real X11 parent under the existing `tools/run_xvfb_test.py` harness, and a host run loop that can record and deliver SDK events/timers. Exercise both `getFrame()->platformOnEvent(event)` for deterministic SDK traversal and **actual XCB button/wheel delivery** for the native postamble. Avoid an independent `SharedPointer<CFrame>` across the close under test, which changes the SDK close branch.

Suggested independently selectable cases:

| Case | Hook and entry | Required observation |
|---|---|---|
| `editor_close_begin_down` | `Handler::on_begin -> IPlugView::removed`, frame/native mouse-down | Begin/end balanced; children survive active traversal; eventual frame gone; no native postamble UAF |
| `editor_close_begin_wheel` | Same hook, wheel event | No stale perform after cancellation; traversal safe; close once |
| `editor_close_perform` | `on_perform -> removed` | Last accepted value retained as specified; one end; no resumed drag |
| `editor_close_end_repeat` | `on_end -> removed` repeated/reentrant | No recursive base teardown, duplicate end, or duplicate timer |
| `editor_close_audition` | `on_allocate` and `on_note -> removed` | Ordered compensation, local owner quiet, sibling owner preserved |
| `editor_close_nested_event` | Host hook dispatches a nested frame event after requesting close | Inner guard exit does not remove children; outer exit still does not destroy native handler prematurely |
| `editor_close_release_owner` | Host releases its external editor reference after `removed` | Deferred owner keeps editor/controller alive; destruction once after safe completion |
| `editor_close_reopen` | Try attach during pending/closing; attach after completion | Explicit rejection during pending, success afterward, stale token cannot affect new frame |
| `editor_close_timer_failure` | Host run loop refuses timer registration | No synchronous structural teardown on active event stack; owner retained without duplicate scheduling; defined retry |
| `editor_close_parent_destroy` | Host destroys parent after `removed` returns | Deferred native teardown tolerates actual host lifecycle or exposes the candidate's limitation |

Run the new close cases with address/undefined-behavior instrumentation where the actual SDK/editor build supports it, and run the real native XCB event cases. Keep existing interaction traces as regression checks. Native Windows/macOS close behavior remains unverified until exercised there; a frame-only pass is insufficient.
