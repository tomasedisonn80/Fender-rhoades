## Independent fixture and oracle

The fixture constructs a real `RhodesController`, initializes it with an `IHostApplication`, connects an `IConnectionPoint`, and uses only `registerAuditionOwner`, `unregisterAuditionOwner`, `auditionNote`, `heldAuditionKey`, `releaseAuditionNotes` and `retryAuditionRelease`. It has no private controller access, processor helper, view implementation or duplicate controller ownership algorithm.

The receiving connection reads literal `RhodesPhotoNoteV1` and `RhodesPhotoReleaseV1` messages and the literal `key`, `down` and `velocity` attributes. It records the acceptance order and applies accepted messages to a separate 73-entry held-key bitmap. Failed release attempts are retained in the trace but do not alter that bitmap. Expected keys and message sequences are literal scenario inputs.

Unlike the existing non-reentrant ownership fixture, this fixture reserves a different message slot **before** invoking the allocation hook. Nested messages cannot overwrite a suspended outer message's ID or attributes. The pool has 64 message objects, with explicit limits on allocation attempts, notification records and callback depth. All callback hooks are moved out and disarmed before invocation; each armed hook must fire exactly once. This prevents the test harness itself from creating an unbounded callback chain.

Construction hooks run during allocation, message-ID installation, attribute-list access, key assignment, down assignment and velocity assignment. Notify hooks separately place the nested emergency before and after the receiver commits the original down. The receiving side snapshots the parsed message before those callbacks, then records it at its actual acceptance point. Failure output includes the scenario and complete wire trace, using `+` for accepted traffic and `-` for rejected traffic.

The only final-state ownership oracle is the controller's public `heldAuditionKey` result. The receiver-held bitmap is checked independently, so cleared controller ownership cannot conceal an accepted orphan down.

## Selectors and requirements

| Selector | Scenarios | Required behavior |
| --- | ---: | --- |
| `construction` | 6 | A nested accepted emergency at each construction boundary cancels the outer down before transmission. The seeded sibling down is followed by exactly one accepted global release. No stale down or redundant emergency follows; a later separate down can succeed. |
| `notify` | 4 | Covers emergency before acceptance and after acceptance, plus allocation and notification failure of the necessary final compensation. Requires a safe final receiver state after accepted cleanup and preserves pending recovery when compensation fails. |
| `pending` | 16 | Eight down boundaries, each with nested emergency allocation failure and notification failure. The original call cancels ownership; construction-time cancellation suppresses the stale down. A failed recovery performs one release attempt. Successful recovery emits only its release and still rejects the requested fresh down in that same call. |
| `siblings` | 16 | Eight down boundaries, each with a same-key or distinct-key sibling close. Ordinary cleanup preserves the active owner and sends no global release. Same-key cleanup sends no premature up; distinct-key cleanup sends only the sibling's up; the final owner sends exactly one up. |
| `coalescing` | 6 | A release-in-progress callback at allocation or before/after release acceptance requests another emergency, an explicit retry and a fresh down. These requests allocate/send no recursive traffic. Both accepted and rejected outer releases preserve their transport outcomes; failed release recovery does not append a fresh down. |
| `all` | 48 | Runs every selector above. |

For a successful construction-time emergency, the literal trace is `Down(12)+, ReleaseAll+`; the pending `Down(40)` must never reach the receiver. This avoids requiring compensation when the controller can still suppress the original message.

For notify-before-accept, the literal safe trace is `Down(12)+, ReleaseAll+, Down(40)+, ReleaseAll+`. The first release cannot cover a down accepted afterward, so a final accepted compensation is necessary. For notify-after-accept, the test accepts either `Down(12)+, Down(40)+, ReleaseAll+` or that trace followed by one compensating `ReleaseAll+`. The sender cannot infer where inside `notify` the receiving side accepted the original down. Both allowed traces end with no receiver-held note and no controller ownership; additional immediate releases fail the bounded-traffic assertion.

The failed-compensation cases deliberately accept the nested release first, then reject the compensation after the original down is accepted. The receiver retains key 40 while cleanup remains pending. The next `auditionNote(..., 42, true, ...)` must emit only an accepted release, report failure for the requested down, and leave every key released. Only a later separate call may start key 42. This distinguishes an acknowledged emergency from completion of the whole in-flight transaction.

For failure before the original send, one nested emergency attempt is permitted. For failure during notify, the fixture allows that attempt and at most one immediate compensation. The subsequent explicit recovery checks are independent of this choice. A failed emergency can temporarily leave a previously accepted note held; the test does not pretend a rejected transport operation has released it. It instead verifies pending cleanup and prohibits newly requested notes until successful recovery has returned.

## Source-derived findings supplied to the integrator

The inspected controller source has the same hashes as the pending-issue snapshot in worker 024's report. `auditionNote` installs an owner's key before `sendAuditionNote`; the latter calls host allocation and attribute methods before sending. `releaseAuditionNotes` clears all keys and can complete its release during one of those callbacks. The original down then resumes without a cancellation check.

Consequently, the baseline is expected to produce `Down(12)+, ReleaseAll+, Down(40)+` in the allocation case, return success, and leave key 40 held at the receiver without an owner. This is a **source-derived prediction**, not a worker-executed runtime reproduction. The root was notified as soon as the fixture design was established and before completion.

The root requested the notify-before-accept case and confirmed that a pre-send cancellation check plus bounded post-notify compensation is a valid direction. The fixture intentionally permits the two safe notify-after traces above. It also verifies release-in-progress coalescing so a nested failure or emergency does not recursively send releases. Ordinary sibling callbacks are separate cases: a transport guard must not turn a routine sibling close into a global cancellation or prevent the active down from completing.
