## Findings

### 1. Native X11 Super shortcuts lose their modifier before reaching the editor

The pinned VSTGUI checkout identifies revision `5db272256172557818b6158cf0bb2c4410bddb25` in its Git metadata. Its `vstgui/lib/platform/linux/x11platform.cpp:227–240` creates a keyboard event from XCB input, mapping Shift, Control and Mod1/Mod5 to the corresponding VSTGUI modifiers. **It does not map Mod4 to Super.** `x11frame.cpp:428–432` forwards the resulting event unchanged.

Consequently, `plugins/vst3/photo_editor.cpp:230–233` correctly rejects an event *containing* Super but cannot reject a native Super+arrow event whose Super bit was discarded. Reproducer for the native validation worker: focus Volume at normalized 0.5, hold a conventionally mapped Mod4/Super key, press Up while that key remains held, then release both. If the host/window manager delivers the chord to the embedded editor, the current source treats it as plain Up and requests 0.51. Plain Up should change the value; Super+Up should produce no edit callbacks. Test all arrow directions and Ctrl/Alt/Shift separately.

The conventional Alt path is already present (Mod1 or Mod5); this audit found **no corresponding ordinary Alt translation omission**. Do not report Alt failure solely by analogy to Super. Host-supplied VST3 key forwarding is a separate path: `public.sdk/source/vst/vstguieditor.cpp:242–260` does represent its supplied shortcut modifiers.

Minimal actual translation fix is to add Mod4→Super at the XCB-key-event boundary through an explicitly recorded dependency patch/overlay, or provide a repository-owned adapter that preserves the raw event's modifier state before view dispatch. A new check of `IPlatformFrame::getCurrentModifiers()` alone will not fix this pin: Linux `x11frame.cpp:721–724` always returns false. A later query of current key/pointer state is not equivalent to event-time state when a queued chord has already been released; any such workaround needs that limitation and rapid-release tests.

### 2. Double-click reset dispatch explains a repeat-toggle failure

`photo_editor.cpp:133–138` tests `clickCount >= 2` before `is_switch(id)`. Both switches default to Off. Starting On, two nearby rapid clicks therefore request **Off, Off**, rather than Off, On. Starting Off produces On, Off, which masks this behavior. The pinned `x11frame.cpp:231–309` classifies the second press as a double click when its elapsed time is below 250 ms and it remains within the five-pixel neighborhood.

This is a source-proven dispatch consequence, not an observed native run in this worker. The existing guide says a double click resets any control, so it also exposes a UX-contract choice: to satisfy independent per-press switch toggling, move the switch branch ahead of double-click reset (or restrict reset to `!is_switch(id)`), then describe default reset as applying to continuous controls. Preserve ordinary knob/slider reset behavior.

Regression coverage should start Sustain and Vibrato in **both** states, issue rapid two- and three-click sequences, and verify every begin/value/end triple and alternating final values. `tools/verify_native_photo_editor.py:326` intentionally waits 0.6 seconds between actions; its existing Off→On→Off checks cannot expose this case.
