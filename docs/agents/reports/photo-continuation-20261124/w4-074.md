# W4-074 — Win32/macOS deferred-close callback lifetime

**Result:** No concrete use-after-free, reference-count, or iterator defect found
in the reviewed completion path. Source inspection only; no platform runtime
result is claimed.

`plugins/vst3/photo_editor.cpp:926–953` retains the editor in
`deferred_close_owner_` before registering the timer. `fire()` first acquires
`keep_alive`, then copies `close_timer_` before clearing that member. Consequently
`stop()` and `close_now()` execute with both objects retained. Clearing the
deferred editor owner cannot delete the editor during the assignment. Reverse
local destruction releases `completing_timer` before `keep_alive`; neither
object is accessed afterward. Pending/reentrant early returns preserve the
timer and deferred owner. The SDK `SharedPointer` copy and `IPtr` construction
actually increment their respective reference counts.

In pinned SDK `vstgui4/vstgui/lib/platform/win32/wintimer.cpp:46–69`, `stop()`
kills registration, erases its map entry, and zeros its handle. Although this
invalidates `TimerProc`'s iterator during `fire()`, `TimerProc` neither dereferences
nor advances it afterward. The timer destructor's subsequent `stop()` is inert.
`cmake/VstguiWin32Timer.cmake:14–16` changes only the successful-start return;
callback retirement remains identical.

In SDK `vstgui4/vstgui/lib/platform/mac/mactimer.cpp:47–64`, `stop()` invalidates
and releases the native timer, then clears its handle. The static callback calls
the raw callback pointer's `fire()` and returns without subsequent pointer or
native-handle access. Its context supplies no separate editor ownership; the
editor's deferred and local owners provide that lifetime.

The ordinary destructor (`photo_editor.cpp:732–738`) stops an existing timer and
closes synchronously without scheduling or retaining itself.

Only this report changed. No builds or tests run. Next: native Windows/macOS
callback-removal runtime verification by the integrator.
