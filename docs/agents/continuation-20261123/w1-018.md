The 12 paired cases completed **4,800 measured callbacks** (2,400 per variant)
and 384 unmeasured warmup callbacks. All 24 benchmark processes returned zero,
reported complete output, and passed **1,008 independent summary, model,
workload, and callback-accounting checks**. The new matrix observed **0/2,400
nominal block-period misses in each variant**. The separately retained earlier
filtered smoke observed **1/10 misses** and remains part of this record.

The result is a short observation of actual processor calls in one shared Linux
container. It supplies neither a worst-case execution-time bound nor a hard

## Scope and design

The [frozen filtered-audio contract](../../specs/FILTERED_AUDIO_20261123.md)
requires complete callback observations separately from filter response and
physical-model validation. This collection times
[`RhodesProcessor::process`](../../../plugins/vst3/processor.cpp) through the
existing [benchmark harness](../../../apps/vst3_benchmark.cpp). It includes host
getters, validation, note ownership, automation, output clearing, rendering,
and mailbox publication. Setup, warmup, lifecycle reset, baseline parameter
flushes, host schedule/sentinel construction, output checking, sorting, and JSON
formatting remain outside the timed region. Clock overhead and OS descheduling
remain inside the observation.

Each process used 73 selected keys, float64 output, 200 measured blocks, and
16 warmup blocks. Held notes cover all combinations of 32,000, 48,000, 96,000,
and 192,000 Hz with 64 and 128 frames. The bounded stress subset adds pedal at
32,000/64 and 192,000/64 and gain at 48,000/128 and 96,000/128. Pedal immediately
releases each struck key and alternates sustain every sample; gain alternates
normalized gain every sample. The harness strikes all selected keys at block
zero and retriggers at the first whole block at or after each half-second
interval. Warmup is followed by a lifecycle and control reset before measurement.

Pair order was shuffled with seed `2026112318`. Variant order alternated by pair
index, starting direct then filtered. Every benchmark subprocess ran serially;
one finite run was made for each case and variant. The matrix ran from
`2026-11-23T16:45:52.874835+00:00` to `2026-11-23T16:45:54.154743+00:00`
with an observed collection interval of 1.279904 seconds. This brief
wall-clock interval is possible because callbacks run back to back, faster than
an audio device would pace them. Each simulated measured stream spans only
0.0667–0.8 seconds, depending on rate and block size; most higher-rate cases
contain only the initial strike.

Both binaries report model/path identity in their JSON. The direct binary
reported model 1, factor 1, host-rate processing, and zero latency. The filtered
binary reported model 2 and 48 frames of latency at every tested rate; factors
were 4 at 32/48 kHz, 2 at 96 kHz, and 1 at 192 kHz. Their reported internal rates
were respectively 128, 192, 192, and 192 kHz. These fields were checked in every
run, rather than inferred from executable names.

At 48 kHz/64 held, for example, the filtered mean was 372.350 µs and observed
maximum 907.744 µs against a 1,333.333 µs nominal period. At 96 kHz/64 held the
filtered maximum was 521.539 µs against 666.667 µs. Those are finite observed
margins, not future scheduling guarantees.

Some cell orderings are counterintuitive: filtered 192 kHz/128 held averaged
106.800 µs while direct averaged 169.452 µs, and filtered 48 kHz/128 gain averaged
less than filtered held at the same rate and block size. With one short run per
cell, uncontrolled shared load, no frequency/affinity control, and different
schedules, these data do not identify the cause or establish a stable speedup,
slowdown factor, or ranking. No such interpretation is used for acceptance.

## Allocation and acceptance limits

Both executables explicitly return `allocation_evidence: "not measured by this
executable"`. The harness allocates its host object and timing vector before the
measurement loop; that placement does not instrument allocation/deallocation
inside processor code, SDK code, or host callbacks. **This experiment provides
no allocation count and no zero-allocation claim.** It also does not instrument
locking, I/O, page faults, or priority inversion. Separate complete-callback
allocator-interception evidence must state allocator coverage and exercised
paths; source review alone and this timing result do not replace that evidence.

Integrity checks establish successful callbacks with finite nonzero output,
matching stereo channels, correct silence flags, expected frame cursors,
expected note ownership, and event/automation getter accounting. They do not
validate a commercial host, plug-in loading, an audio device, another platform,
float32 callbacks, all block sizes, sustained tail behavior, or every event
schedule. No antialiasing, physical fidelity, audibility improvement, or release
acceptance follows from the timing matrix. The synthetic boundary and broader
RT-001/HOST-001 obligations remain unchanged.
