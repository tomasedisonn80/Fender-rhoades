# W3-045 — Current upload action runtime compatibility

Date: 2026-11-23. Worker: actual continuation worker 45/100, wave 3.
Scope: `.github/workflows/vst3.yml` and this report only.
The integrator retains Git publication, state, claims and evidence registration.

## Decision and change

Replace the newly introduced `actions/upload-artifact` v4.6.2 pin
`ea165f8d65b6e75b540449e92b4886f43607fa02` with the verified v7.0.2 commit
`cf430e030ddbb5b0abf93d22962f4752f3646cd9`.
This changes exactly one workflow line, including its version comment.
Archive Python, SDK revisions, checkout/setup pins, matrix and inputs are unchanged.
The immutable earlier [W2-038 report](w2-038.md) remains untouched.

GitHub's [2026-09-23 runtime notice][node24] states that Node 20 has been removed
from runners, JavaScript actions now use Node 24, and users should select action
versions supporting Node 24. The old [v4.6.2 manifest][old-manifest] declares
`node20`; the new [pinned manifest][manifest] declares `node24`.
This supports selecting the current upstream runtime explicitly. It does not
prove that the older pin would fail under GitHub's runtime migration.

## Official provenance and compatibility

All upstream sources below were read on 2026-11-23 using GitHub's public API,
official repository files, documentation or changelog; no third-party source was used.

- The [latest release endpoint][latest] returned v7.0.2, published
  `2026-10-07T10:08:14Z`, with `draft: false` and `prerelease: false`.
  The [tag ref][tag] resolves directly to commit
  `cf430e030ddbb5b0abf93d22962f4752f3646cd9`.
  The workflow pins that commit, not the mutable tag; the release's
  `immutable` field itself was `false`.
- The [Git commit response][commit] reports `verification.verified: true`,
  reason `valid`. This is GitHub's verification response, not a local signature check.
- The [v6 runtime release][v6] documents Node 24 and Actions Runner >=2.327.1.
  The v7.0.2 manifest retains Node 24; the [v7 release notes][v7] introduce ESM
  and optional direct uploads without documenting a higher runner minimum.
  The workflow uses GitHub-managed `ubuntu-latest`, `windows-latest` and
  `macos-latest`; GitHub [maintains and upgrades those runners][hosted].
  Compatibility is an assessment from these contracts; actual runner version and
  execution still require job logs. The plug-in's macOS deployment target 11.0
  is a binary target, not the host OS running the JavaScript action.
- All five existing upload inputs are present in the pinned manifest:

  | Input | Retained value / behavior |
  |---|---|
  | `name` | `${{ steps.vst3-archive.outputs.name }}` |
  | `path` | `${{ steps.vst3-archive.outputs.path }}`; required single archive path |
  | `if-no-files-found` | `error`; fail if the archive is missing |
  | `retention-days` | `7`; within the documented 1–90 day range |
  | `compression-level` | `0`; valid 0–9 range, no redundant ZIP compression |

- The new `archive` input defaults to `true`, retaining the named outer ZIP
  containing the existing `.tar.gz`. `archive: false` would ignore `name` and
  use the uploaded filename; that option is deliberately not enabled.
  [Pinned usage documentation][readme] accepts relative paths rooted at the
  current working directory. The archive producer and upload retain the same
  workspace-relative `build/vst3-artifacts` path, with no working-directory change.
  Default hidden-file exclusion cannot remove entries already inside the tar.
  The tar continues to carry bundle modes and links; outer ZIP modes are irrelevant
  to its contents. No additional token, permission or API call is configured.
- The [pinned license][license] is MIT, copyright 2018 GitHub, Inc. and contributors.
  No action source is vendored and no project license decision is changed.
  v4+ remains unsupported on GitHub Enterprise Server according to the pinned
  README; this workflow targets github.com, not GHES.
