## Changes

Only the assigned `tests/cpp/vst3_test_support.hpp` and
`tests/cpp/vst3_host_test.cpp` were changed, plus this report.

- `ProcessorHost` heap-owns its processor while retaining the existing
  `.processor` reference interface and explicit termination lifecycle.
- `ProcessorSnapshot` heap-owns its saved event processor and both independent
  continuation engines. Its `.engine` interface still supports existing callers.
- The host suite heap-owns the dense fixture/buffers, large parameter queues,
  scalar reference engines, standalone event-processor copies and unconfigured
  processor fixture. The small reference aliases preserve the original assertions.
- All ownership uses standard `unique_ptr`. Construction, snapshotting,
  comparisons and destruction remain outside the allocation-probed `process()`
  interval. No callback allocation suppression or stack-limit increase was added.

The tested callback wrapper and all eight calibrated allocation replacement
forms are unchanged. Numerical, state, ownership, buffer-guard and future-output
assertions remain intact. No production, build-system or canonical-state files
were edited.

## Actual verification

On Linux with the existing Release/GCC build and pinned SDK:

```sh
cmake --build build/vst3 --target rhodes_vst3_host_tests rhodes_vst3_filtered_regression_tests --parallel 2
ctest --test-dir build/vst3 -C Release -R '^vst3\.(filtered_regression_)?(scalar_output|overlapping_notes|linear_automation|dense_automation|invalid_atomicity|parameter_flush|lifecycle|deferred_state|recall_abort|stream_errors|controller_mapping|allocation_guard)$' --output-on-failure --no-tests=error --parallel 2
git diff --check -- tests/cpp/vst3_host_test.cpp tests/cpp/vst3_test_support.hpp
```

Both target builds succeeded; **24/24 CTests passed**, including both allocation
guards. The scoped whitespace check passed. The build log is a temporary local
artifact at `/workspace/scratch/a37aa07d1094/w1-a19-build.log`.

A separate focused Python `subprocess.run` invocation used `resource.setrlimit`
in each child's `preexec_fn` to set `RLIMIT_STACK`'s soft limit to **1,048,576
bytes**, leaving the hard limit unchanged. Both executables passed
`dense_automation` and `invalid_atomicity`: **4/4 capped-stack invocations**.
Their outputs reported respectively 5 and 29 allocation-guarded callbacks,
with all eight allocation forms calibrated, for each variant.
