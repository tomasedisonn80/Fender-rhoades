## Exact failures and bounded remedies

### Windows VST3 compilation

The job log reports C2220 because warning C4458 is treated as an error at
`plugins/vst3/controller.cpp:86`: `RhodesController::queryInterface` names its
parameter `iid`, hiding inherited `Steinberg::FObject::iid`. Both direct and
filtered module builds fail here.

Exact diagnostic excerpt: `warning C4458: declaration of 'iid' hides class member`.

Rename the argument in the declaration/definition and its three uses to
`interface_id`. Preserve `/W4 /WX`; this is a project-source shadowing defect,
not justification to suppress warnings in the SDK or workflow.

### Windows manifest provenance keys

`test_contact_extension.ContactExtensionTests.test_generated_manifest_carries_declared_policy_into_audit_command`
and
`test_contact_peak_sweep.ContactPeakSweepTests.test_success_binds_request_raw_streams_and_unchanged_audit_invocation`
fail because `source_sha256` uses keys such as
`docs\\specs\\CONTACT_REFINEMENT_EXTENSION_20261123.md`, while the portable
manifest contract uses repository-relative forward slashes.

`tools/run_contact_sweep.py:317` serializes `str(path.relative_to(ROOT))`.
Use `path.relative_to(ROOT).as_posix()` for these portable identifiers. Preserve
hashes of the actual source bytes; do not normalize content bytes or alter the
expected policy names in tests.

### Windows documentation path classification

The two `/etc/passwd` and `%2fetc/passwd` subcases of
`test_docs.DocumentationTests.test_absolute_and_encoded_absolute_paths_are_rejected`
fail. The checker rejects both as escaping the repository, but emits the wrong
category because native Windows `Path('/etc/passwd').is_absolute()` is false
without a drive. `tools/check_docs.py:146` combines that method with a drive-path
regex and misses root-relative paths.

Exact returned diagnostic: `README.md:1: local link escapes repository: '/etc/passwd'`.

Classify decoded POSIX-rooted and Windows-rooted links explicitly before
resolution. Keep rejecting encoded roots and traversal; do not weaken the test
to accept arbitrary diagnostics.

The hosted Windows Python invocation ran 376 tests, with four failed subcases
and 16 skips. Earlier project-state, data, documentation, ledger, and coefficient
checks in that job succeeded.

### Windows symlink preservation fixtures

Windows CTest ran 131 tests and failed only:

- `cli.render_output`: `tests/cpp/render_output.cmake:97`, reporting changed
  dangling-symlink destination.
- `cli.filtered_render`: `tests/cpp/filtered_render.cmake:171`, reporting changed
  live-symlink destination.

Both fixtures compare `file(READ_SYMLINK ...)` with the original CMake path string.
On Windows the returned symlink target can contain native separators, while
CMake's constructed input uses forward slashes. The tests already observed the
renderer correctly rejecting both normal and forced symlink output before the
comparison failed. Therefore the present log does not demonstrate mutation of
the target.

Read the actual symlink target immediately after creation, then require an exact
match to that snapshot after all rejected renders. This verifies preservation
without presuming how the host serializes a newly created link. Retain target
content checks and dangling-target non-creation checks. This inference should be
confirmed by the next Windows hosted execution.
