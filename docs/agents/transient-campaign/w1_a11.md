## Priority recommendations

1. Keep the approximately 84,096-byte observation matrix plan as persistent
   instance storage belonging only to the new engine. Six 96-cell double
   histories add 4,608 bytes. These are layout-independent array payload counts,
   not measured `sizeof` values. Existing direct/filtered instances should not
   acquire this cost.
2. Build transactional candidates only during explicit preparation. Validate
   host rate before constructing large candidates; avoid nested default engine
   construction that performs a redundant 48 kHz preparation. An observation
   plan factory and wrapper can otherwise retain several 84 KB temporaries on
   the preparation stack. This is outside the audio callback, but still relevant
   to host stack limits.
3. `reset`, note/pedal events and deferred state recall must not reconstruct the
   plan or run trigonometric/exponential functions. Reset should retain the
   rate-bound immutable plan and clear only mechanical state, ring history and
   phase index. `processor.cpp::install_recall` runs at the audio boundary and
   calls `engine_.reset()`; rebuilding there would put preparation into callbacks.
4. Preserve the current preflight pattern: `RhodesProcessor::process` copies a
   `NoteTracker`, never the complete engine. Stage six observed scalar voltages
   in a small local array; do not copy the complete wrapper each frame or block
   to implement rollback. Retain the existing explicit fault/reset policy.

## Concrete test-stack hazard

`tests/cpp/vst3_test_support.hpp::ProcessorSnapshot` stores a complete
`HostEventProcessor`. Its `expect_unchanged` method additionally copies both
the observed and expected engines to compare future trajectories. The current
`dense_automation` fixture in `vst3_host_test.cpp` already keeps a processor,
8195-frame stereo buffers, two 8192-point parameter queues and a snapshot on
the stack. Adding approximately 88.7 KB to each engine can push the nested test
stack beyond a typical 1 MB Windows executable stack budget. This is a concrete
source-level risk, not an observed stack-overflow result in this review.

Heap-own the large host fixtures, snapshots and continuation engines outside
the allocation-probed `process()` interval, or otherwise establish a bounded
stack layout. Do not hide a runtime allocation by moving it inside the callback,
and do not merely raise every executable's stack limit. The benchmark already
uses `std::make_unique<Host<Sample>>`, so its large host object has the preferable
ownership pattern. Other model-3 test fixtures need the same inspection.

## Callback verification and benchmark identity

The existing host test replaces ordinary, array, aligned and nothrow C++
allocation operators and calibrates all eight forms. Reuse it for model 3,
including parameter-only flush, deferred recall, malformed late input and both
sample formats. Extend rate coverage to 32 kHz and the existing branch-boundary
rates where meaningful. This only measures covered allocation paths; it is not
proof of all real hosts or every external allocator.

The new plan uses nonuniform fractional observations, not a uniform higher
sample rate. `apps/vst3_benchmark.cpp` currently emits an oversampling factor and
internal sample rate from its filtered flag. Add a distinct audio identity,
quadrature order 6, and an explicit host-rate boundary clock. Do not describe
Q6 as six-times oversampling. Preserve complete callback timing, observed
maxima/deadline misses, workload and environment fields.

The proposed path performs six modal/pickup/network observations plus one
legacy boundary advance and 576 FIR multiply-accumulates per frame. These are
operation counts, not CPU measurements. At 192 kHz it replaces a one-substep
filtered path, so actual callback cost needs measurement before any performance
claim. Measure idle and active/retrigger/pedal workloads separately; retain
failures and do not infer real-time acceptance from a fast average.
