## Recommended probe boundary

Build a separate **`rhodes_quadrature_probe`** executable from the existing
bounded parser/dispatcher source, using a target-private
`RHODES_QUADRATURE_PROBE` definition and an explicit engine/metadata trait.
Keep `rhodes_audio_probe`'s exact arguments, default engine, model identity,
metadata and error behavior. No runtime mode flag is needed for the numerical
probe; the binary and emitted model identity already identify its contract.

In `apps/audio_probe.cpp`, make the engine alias, `apply` signature, error/help
prefix and metadata emission variant-aware. Keep the parser, 4096-frame/event
limits, 128-byte line bound, full preflight, ordered physical dispatch,
double-precision output and final stdout flush shared. Use a heap-owned large
engine after preflight if necessary for native stack limits; this is an offline
exporter, not an audio-callback allocation test.

For the new probe, emit `schema_version: 1`,
`model: "synthetic-quadrature-audio"`, `sample_rate_hz`, `latency_frames: 48`,
`quadrature_nodes: 6`, `observation_scheme: "gauss-legendre-host-cell"`, and the
existing frame/event/sample fields. Do **not** emit `oversampling_factor` or
`internal_sample_rate_hz`: nonuniform observations are not a uniformly sampled
signal. The waveform remains unscaled loaded volts with the requested duration,
startup, reset samples and causal delay retained.

## Renderer edits

Add `quadrature` to `AudioPath`, help, option parsing and final template dispatch
in `apps/render.cpp`. The default remains `direct`. Add a path-info overload for
the new engine, representing node count explicitly. Preserve old success text
for direct/filtered; the quadrature success message should name six fractional
observations per host cell and 48-frame latency, without a fictitious internal
uniform rate. Reuse the existing transactional WAV staging/publication, float32
range check, gain, exact frame count and release timing without modification.

The renderer deliberately accepts integer WAV rates, whereas the JSON probe
accepts binary64 rates. Keep this distinction; the probe is needed for exact
`nextafter` boundaries in the nine-rate numerical matrix.
