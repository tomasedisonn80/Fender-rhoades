# Wave 3 assignment 41 — Quadrature campaign validation

## Scope and result

Added `tools/quadrature_campaign.py` and
`tests/python/test_quadrature_campaign.py`, and added two checks to
`.github/workflows/ci.yml`. The existing setup, development and continuation
campaign checks remain unchanged. No canonical ledger, existing report, generated
index, project state or Git history was modified by this assignment.

The new standard-library tool validates the existing quadrature ledger and can
regenerate only its Markdown index. It provides `validate`, optional
`validate --require-complete`, `sync`, and read-only `sync --check`; `--root`
selects an isolated repository for tests. It has no registration, completion,
rehashing or worker-launching command.

Validation requires the declared 100 assignments, five waves of 20 and three
concurrent-worker limit. Returned records must be completed, ordered consecutively
from one, and have the expected wave, distinct actual-agent identifier and report
path. It checks nonempty scopes, report presence, SHA-256 syntax and bytes, and
rejects reused report content. Completed-wave claims must equal the full groups
of 20 returned reports. The optional final gate requires all 100 records.

Strict JSON parsing rejects duplicate keys, nonfinite values and overflow to
infinity. Paths use a canonical relative spelling, remain within the selected
root, and reject symlink components. Index publication validates the complete
ledger before an atomic replacement; failure preserves the preceding files.

The generator reproduces the current 40-assignment index byte-for-byte. It keeps
the assignment-40 correction of assignment 38: the host bound is 8192 frames or
parameter points; the underlying event processor bound is 4096 frames, with
one-frame calls from the host. The original returned report remains unchanged.

These checks establish consistency of recorded identifiers and artifact bytes.
They cannot attest actual spawning, concurrency, execution, work acceptance or
physical fidelity. Only the integrator may record actual returned assignments.

## Verification actually run

```sh
python3 tools/project.py validate
python3 tools/project.py sync --check
python3 tools/project.py next --json
python3 -m unittest discover -s tests/python -p test_quadrature_campaign.py -v
python3 -S -m unittest discover -s tests/python -p test_quadrature_campaign.py -v
python3 tools/quadrature_campaign.py validate
python3 tools/quadrature_campaign.py sync --check
python3 tools/quadrature_campaign.py validate --require-complete
python3 tools/check_docs.py
git diff --check
```

Both final focused unittest executions passed **15 tests with zero skips** on
Linux. The `-S` run confirms that the suite requires only the standard library.
All fabricated 0–100-record histories belong to temporary test directories and
explicitly identify themselves as synthetic fixtures; they never enter the
actual campaign ledger.

The first focused run found that the generic path helper accepted `.`. The guard
was corrected to reject paths with no components, and both final runs passed.
Other negative fixtures cover identity duplication, gaps and reordering, boolean
integer substitutions, false completed-wave claims, unsafe or reused report
paths, changed or missing reports, reused content, malformed JSON, stale indexes,
symlinks and injected atomic-publication failure.

Current-ledger validation and index drift checking passed for **40 returned
assignments and two completed waves**, without changing either file. The strict
completion command correctly exited **1** with “require 100 completed reports”;
this was the expected result while the campaign was still in progress. Project,
documentation and whitespace checks passed. No broad DSP tests or hosted CI jobs
were rerun for this tooling-only change.
