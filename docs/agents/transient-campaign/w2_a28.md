# Wave 2 assignment 28 — VST3 quadrature benchmark identity

## Scope and result

Implemented the model-3 benchmark metadata and startup-output contract in
`apps/vst3_benchmark.cpp` and `tests/cpp/vst3_benchmark_json.cmake`. The benchmark
uses the actual quadrature processor selected by worker 25's variant wiring and
worker 27's private CMake target definition. No Git, canonical state, CMake or
other implementation paths were changed by this assignment.

The quadrature executable identifies itself as
`rhodes_vst3_quadrature_benchmark`; JSON reports `Rhodes Research Quadrature`,
state model 3, 48 latency frames, six quadrature nodes and observation scheme
`gauss-legendre-host-cell`. Both `oversampling_factor` and
`internal_sample_rate_hz` are absent because the six observations are not a
uniform-rate oversampling stream. The direct and filtered variants retain their
existing identity fields and values. All variants keep JSON schema version 1.

The measured phase resets after warmup. With quadrature, its first output sample
has no completed host cell and is exactly zero even when keys are struck.
`nonzero_output_expected` is therefore false only for an excited quadrature run
requesting exactly one block of exactly one frame. Every longer excited run
still requires nonzero output. Silence flags, cursor, getter counts, ownership,
finite output and all other completion checks remain required.

The CMake fixture accepts `EXPECT_AUDIO_PATH=quadrature` and preserves the
existing `EXPECT_FILTERED=OFF/ON` callers. The new selector also accepts the
explicit names `direct` and `filtered`; supplying both selector forms rejects as
ambiguous. Quadrature identity tests require the six-node observation metadata
and absence of both uniform-rate fields. Legacy identity tests require their
existing uniform-rate fields and absence of quadrature metadata.

## Verification actually run

Commands were run on Linux x86_64 with GCC 14.2.0, CMake Release configuration and
the supplied pinned VST3 SDK at
`/workspace/scratch/a37aa07d1094/vst3sdk`. Worker 27 had configured the isolated
`build/w2-a27-vst3` directory before this assignment compiled the targets.

```sh
python3 tools/project.py validate
python3 tools/project.py sync --check
python3 tools/project.py next --json
cmake --build build/w2-a27-vst3 --config Release --target rhodes_vst3_benchmark rhodes_vst3_filtered_benchmark rhodes_vst3_quadrature_benchmark --parallel 2
ctest --test-dir build/w2-a27-vst3 -C Release -R '^vst3\.(filtered_|quadrature_)?benchmark_json$' --output-on-failure --no-tests=error -V
```

State validation passed for 14 tasks and 16 evidence records; generated state
was current. `next --json` reported no unclaimed ready work, consistent with the
integrator's existing claims and this bounded assignment. All three benchmark
targets compiled successfully. All three selected CTests passed:

| Variant | Workload JSON cases | Rate/format identity cases | Invalid-input cases | Help |
| --- | ---: | ---: | ---: | --- |
| Direct | 22 | 12 | 23 | Passed |
| Filtered | 22 | 12 | 23 | Passed |
| Quadrature | 40 | 12 | 23 | Passed |

The 12 identity cases cover 32/64-bit output at 32000, 48000, 48001, 96000,
96001 and 192000 Hz. Existing warmup equivalence, all three workloads, retrigger,
silence, output checksums/fingerprints, getter accounting, raw callback records,
deadline arithmetic and nearest-rank summary checks remain active.

The additional 18 quadrature cases cover held, pedal and gain workloads in both
sample formats. Each checks a one-frame measurement after warmup, a two-frame
single callback and two consecutive one-frame callbacks. The latter two must
have identical output fingerprints and nonzero output. The original cold
one-frame case also passes, with exactly zero output for quadrature.

An initial CTest command used executable-style names in its regular expression
and selected no tests (exit 8). The generated CTest names were then inspected,
the filter was corrected to the command above, and all three intended suites
ran and passed. No broad performance benchmark was run; callback observations
inside these functional fixtures are not performance acceptance evidence.

## Limits and handoff

These results establish local executable/JSON behavior against the in-process
SDK adapter. They do not establish native Windows/macOS execution, module-loader
or commercial-DAW behavior, callback deadline safety, allocation policy or
measured instrument fidelity. The model remains synthetic and fidelity remains
unvalidated. The integrator can now use the separately identified quadrature
benchmark for its planned reproducible timing observations after integration.
